= ADR 0046: RFC 9457 Problem Details als Fehlerformat der API

== Status

Akzeptiert – 2026-08-16

Löst das bis dahin selbst erfundene `ErrorResponse`-Format ab. Die Currying-Regel aus
link:0021-currying-fuer-records-mit-mehr-als-zwei-komponenten{adrext}[ADR 0021] gilt
unverändert und greift für den neuen Record ebenso.

== Kontext

Die API antwortete auf jeden Fehler mit einem eigenen Format:

[source,json]
----
{ "status": 400, "error": "VALIDATION_FAILED", "message": "…", "fieldErrors": [ … ] }
----

Das ist in sich stimmig, aber *projektlokal*. Drei Punkte sprechen dagegen:

. *Es ist nicht wiedererkennbar.* Ein fremder Client muss das Format lesen, statt es zu kennen.
  Für genau diesen Zweck gibt es
  https://www.rfc-editor.org/rfc/rfc9457.html[RFC 9457 „Problem Details for HTTP APIs"] – den
  Nachfolger von RFC 7807, den Bibliotheken und Werkzeuge bereits auswerten.
. *Der Medientyp sagt nichts.* Die Antworten trugen `application/json`; ein Client kann eine
  Fehlerantwort damit nicht am Medientyp erkennen, sondern nur am Statuscode.
. *Der Fehler nennt seinen Ort nicht.* Weder die *Art* des Problems (ein Bezeichner, der über
  Versionen stabil bleibt) noch die *betroffene Anfrage* standen in der Antwort. Beides gehört
  nach RFC 9457 hinein (`type`, `instance`).

Hinzu kommt: Nur die vier selbst behandelten Fälle hatten überhaupt ein Format. Ein `405`, ein
`415` oder ein unbekannter Pfad fielen auf Spring Boots Standardseite zurück – ein zweites
Fehlerbild neben dem eigenen.

== Optionen

. *Nichts ändern.* `ErrorResponse` bleibt. Kostenlos, aber die drei Punkte oben bleiben auch.
. *Spring `ProblemDetail` verwenden* (`org.springframework.http.ProblemDetail`), zusammen mit
  `spring.mvc.problemdetails.enabled=true` und `ResponseEntityExceptionHandler`. Der kürzeste
  Weg – aber die Feldfehler wären *Extension Members* in einer `+Map<String, Object>+`. Der
  OpenAPI-Contract beschreibt sie dann nicht, und damit verliert das Frontend seine
  *generierten* Typen: `+ApiError.fieldError(feld)+` stünde wieder auf einer handgeschriebenen
  Deklaration (`docs/system/api.adoc`, „Abgeleitete TypeScript-Typen").
. *Eigener Record in der Form von RFC 9457* – `type`, `title`, `status`, `detail`, `instance`
  und `fieldErrors` als typisiertes Erweiterungsfeld, ausgeliefert als
  `application/problem+json`. Mehr Code als Option 2, dafür bleibt der Contract vollständig und
  das Frontend generiert.
. *Option 3 plus `spring.mvc.problemdetails.enabled=true`* – zusätzlich antwortet auch das
  Framework auf die Fälle, die nie einen eigenen Handler hatten (`405`, `415`, `406`), im
  Problem-Format.

== Entscheidung

*Option 4.*

=== Der Record

`ProblemDetail` im Paket `adapter.in.rest` trägt die fünf Felder aus
RFC 9457 und `fieldErrors` als Erweiterung. Alle sechs sind im Contract `required`; `detail`
fällt auf den `title` zurück, wenn eine Ausnahme keine Meldung mitbringt, und `fieldErrors` ist
außerhalb der Validierung eine *leere* Liste, nie `null`. Das Frontend darf sich darauf
verlassen, ohne zu prüfen.

Der Name ist absichtlich der Begriff des RFC, obwohl Spring eine gleichnamige Klasse mitbringt.
Sie wird hier nicht importiert; der Contract heißt, wie die Spezifikation die Sache nennt.

=== Die Problemarten

`ProblemType` zählt sie auf: `not-found`, `validation-failed`,
`malformed-request`, `invalid-argument`. Jede kennt ihren Titel und ihren Statuscode – der
Handler wählt die Art, nicht die drei Werte einzeln.

=== Die `type`-URI zeigt auf die Dokumentation

RFC 9457 empfiehlt, dass die URI beim Auflösen eine *menschenlesbare* Beschreibung liefert.
Deshalb ist sie kein erfundener Domänenname und keine URN, sondern der Anker der
ausgelieferten Systemdokumentation:

----
/recipes/docs/#problem-not-found
----

Der Präfix stammt aus `+request.getContextPath()+`, nicht aus einer Konstanten – der
Context-Path aus link:0016-context-path-recipes{adrext}[ADR 0016] steht damit *nicht* an einer
weiteren Stelle im Code. `instance` ist `+request.getRequestURI()+` und benennt die konkrete
Anfrage.

=== Das Framework antwortet mit

`+spring.mvc.problemdetails.enabled: true+` in `application.yml` lässt Spring die Ausnahmen
beantworten, die nie einen eigenen Handler hatten. Damit der eigene Handler die vier bekannten
Fälle behält – Spring registriert seinen mit `+@Order(0)+` –, trägt
`GlobalExceptionHandler` `+@Order(HIGHEST_PRECEDENCE)+`.

== Konsequenzen

*Vorteile*

* Fehlerantworten sind an `+application/problem+json+` erkennbar, ohne den Rumpf zu lesen.
* `type` ist ein stabiler Bezeichner *und* ein Verweis auf die Beschreibung des Falls.
* `instance` nennt die Anfrage – im Protokoll einer Fehlermeldung steht damit, welche.
* Auch `405` und `415` tragen jetzt ein Fehlerformat statt der Standardseite.
* Der Contract beschreibt das Format vollständig; `schema.d.ts` bleibt generiert.

*Nachteile*

* Der Record dupliziert, was Spring in `ProblemDetail` schon anbietet – der Preis für die
  typisierten `fieldErrors` (Option 2).
* Es sind zwei Fehlerformate im Umlauf: das eigene für die vier bekannten Fälle, Springs
  eigenes für die Fälle des Frameworks. Sie sind bis auf `fieldErrors` gleich geformt; das
  Frontend behandelt das Feld deshalb als optional, obwohl der Contract es garantiert.
* Die `type`-URI ist nur auflösbar, solange die Dokumentation unter `/recipes/docs/` liegt
  (link:0024-systemdokumentation-im-boot-jar{adrext}[ADR 0024]). Verschwindet sie, zeigen die
  URIs ins Leere, ohne dass etwas rot wird.
* Ein Client, der `+message+` oder `+error+` gelesen hat, bricht. Die API ist unversioniert;
  der einzige bekannte Client ist die mitgelieferte SPA und wird mitgezogen.

*Bewusst nicht getan*

* *Kein `500`-Handler.* Eine unerwartete Ausnahme bleibt bei Springs Behandlung – ein eigener
  Handler müsste entscheiden, was er preisgibt, und wäre damit eine Sicherheitsentscheidung
  (`docs/prompt/security.adoc`). Bis dahin ist die Standardantwort die vorsichtigere.
* *Keine Erweiterung um `errors`* nach dem Vorbild von RFC 9457, Abschnitt 4.2.2
  („Multiple Problems"). `fieldErrors` deckt den einzigen Fall ab, den die API kennt.
* *Kein `Retry-After`, kein `Content-Language`.* Es gibt weder Rate Limiting noch
  Mehrsprachigkeit; beides steht im Backlog.

== Prüfung

* `RecipeControllerTest` – prüft `not-found`, `validation-failed` und `malformed-request` über
  Statuscode, Medientyp, `type`, `title`, `detail`, `instance` und die Feldfehler, dazu einen
  `405` aus Springs Handler. `invalid-argument` bleibt ohne eigenen Test: Die Bean Validation
  fängt jede Eingabe vorher ab, die eine Domäneninvariante verletzen würde – der Fall ist über
  den Endpunkt nicht auslösbar, nur über einen Aufruf am Controller vorbei.
* `CurriedFactoryTest` – die Kette von `ProblemDetail` liefert dasselbe wie der kanonische
  Konstruktor; `RecordCurryingTest` prüft ihre Form (ADR 0021).
* `SwaggerSystemTest` – der Contract führt `ProblemDetail` mit allen sechs Pflichtfeldern, und
  die laufende Anwendung antwortet auf einen unbekannten Bezeichner genau so.
* `./gradlew test systemtest e2eTest` – grün.
