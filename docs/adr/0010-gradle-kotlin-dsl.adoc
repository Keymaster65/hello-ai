= 0010 – Gradle-Buildskripte in der Kotlin-DSL

== Status

Akzeptiert und umgesetzt +
Datum: 2026-08-09

== Kontext

Das Buildskript ist über die Sessions deutlich gewachsen: jOOQ-Codegen, ein zusätzliches
Source-Set für Systemtests (link:0006-testsets-plugin-und-systemtests{adrext}[ADR 0006]),
vier `Exec`-Tasks für den Frontend-Build
(link:0007-react-frontend-mit-backend-als-bff{adrext}[ADR 0007]) und die E2E-Suite
(link:0008-playwright-fuer-e2e-tests{adrext}[ADR 0008]). In der *Groovy-DSL* ist all das
dynamisch typisiert: Tippfehler in Task- oder Property-Namen fallen erst zur Laufzeit auf,
die IDE kann kaum navigieren oder vervollständigen. Da das Projekt ohnehin auf statisch
typisierte Sprachen setzt (Java 25, TypeScript im `strict`-Modus), passt eine dynamisch
typisierte Build-Sprache schlecht ins Bild.

== Optionen

. *Kotlin-DSL* (`+build.gradle.kts+`) – statisch typisiert, Autovervollständigung und
  Refactoring in der IDE, Fehler zur Konfigurationszeit.
. *Groovy-DSL beibehalten* – kein Aufwand, aber die genannten Nachteile bleiben.
. *Version Catalog + Groovy* – löst nur die Abhängigkeitsverwaltung, nicht die Typisierung.
. Wechsel auf ein anderes Build-Tool (Maven) – unverhältnismäßig.

== Entscheidung

*Option 1.* `+build.gradle+` und `+settings.gradle+` wurden nach `+build.gradle.kts+` bzw.
`+settings.gradle.kts+` überführt, die Groovy-Dateien entfernt. Inhaltlich ist der Build
unverändert; es wurden keine Tasks, Abhängigkeiten oder Optionen hinzugefügt oder
weggelassen.

== Konsequenzen

*Vorteile*

* Fehler in Task- und Property-Namen fallen bereits bei der Konfiguration auf, nicht erst im
  Lauf.
* IDE-Unterstützung: Autovervollständigung, „Gehe zu Definition", sicheres Umbenennen.
* Einheitliche Typdisziplin über Backend, Frontend und Build.

*Nachteile*

* Erste Konfiguration nach einer Änderung ist langsamer, weil das Skript kompiliert wird
  (danach greift der Cache).
* Die Kotlin-Laufzeit (`+kotlin-stdlib+`, `+kotlin-reflect+`) kommt als Build-Abhängigkeit
  dazu und muss einmalig geladen werden.
* Beispiele im Netz und in Plugin-READMEs sind häufig in Groovy formuliert und müssen
  übersetzt werden – siehe die Fallstricke unten.

== Fallstricke bei der Übersetzung

Drei Stellen ließen sich nicht mechanisch übertragen:

. *jOOQ-Codegen.* Die Groovy-DSL verschachtelt Closures
  (`+generationTool { generator { database { properties { property { … } } } } }+`). In Kotlin
  wird stattdessen direkt auf den JAXB-Objektbaum zugegriffen:
  `+jooqConfiguration.apply { generator.apply { database.apply { properties = listOf(Property().withKey(…).withValue(…)) } } }+`.
  Die booleschen Schalter heißen dort `isRecords`, `isPojos`, `isDaos`, `isFluentSetters`
  (JavaBeans-Konvention), nicht `records`, `pojos`, … Nötig sind die Importe
  `+org.jooq.meta.jaxb.Logging+` und `+org.jooq.meta.jaxb.Property+`.

. *Konfigurationen aus dem testsets-Plugin.* `+systemtestImplementation+` entsteht erst, wenn
  `+testSets { create("systemtest") }+` gelaufen ist. Für dynamisch erzeugte Konfigurationen
  gibt es im selben Skript *keine* typsicheren Accessoren; sie werden über ihren Namen als
  String angesprochen: `+"systemtestImplementation"("…")+`.

. *Gemeinsame Task-Inputs.* Der Groovy-Trick, eine Closure in einer Variablen zu halten und
  mit `configure` anzuwenden, hat in Kotlin kein Gegenstück. Stattdessen eine
  Erweiterungsfunktion: `+fun Exec.frontendSources() { … }+`, aufgerufen im jeweiligen
  Task-Block.

== Nachweis der Gleichwertigkeit

Die Migration wurde nicht nur „grün gebaut", sondern gegen den vorherigen Stand geprüft
(2026-08-09):

* Der von `generateJooq` erzeugte Code ist *byte-identisch* zum Ergebnis des Groovy-Builds
  (`+diff -r+` über alle 11 Dateien ohne Unterschied). Das ist der aussagekräftigste Test,
  weil der jOOQ-Block die komplexeste Übersetzung war.
* `+./gradlew clean build+` grün (23 Java-Tests, 24 Vitest), Boot-Jar enthält die SPA.
* `+./gradlew systemtest+` 13/13, `+./gradlew e2eTest+` 7/7.
* Die Schalter `-PskipFrontend`, `+-Psystemtest.baseUrl+` und `+-Pe2e.baseUrl+` verhalten sich
  unverändert.

== Regel für die Zukunft

* Neue Build-Logik wird in `+build.gradle.kts+` ergänzt; `+.gradle+`-Dateien in Groovy werden
  nicht wieder eingeführt.
* Plugin-Dokumentation in Groovy vor der Übernahme übersetzen – insbesondere bei
  verschachtelten Closures, die auf JAXB- oder POJO-Bäume abbilden.
* Konfigurationen, die erst zur Konfigurationszeit entstehen, über ihren String-Namen
  ansprechen statt auf Accessoren zu warten, die es nicht gibt.
