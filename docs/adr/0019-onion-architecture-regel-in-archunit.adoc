= 0019 – ArchUnit prüft die Struktur zusätzlich als Zwiebelschalen

== Status

Akzeptiert und umgesetzt +
Datum: 2026-08-09

== Kontext

link:0012-archunit-fuer-die-schichtenregel{adrext}[ADR 0012] sichert die Regel
`+bootstrap → adapter → application → domain+` mit `+layeredArchitecture()+` ab. Diese Sicht
kennt aber nur *eine* Adapter-Schicht: `+..adapter..+`. Damit ist ein Zugriff des
REST-Adapters auf den Persistenz-Adapter – etwa ein Controller, der direkt am generierten
jOOQ-Code hängt und den Port umgeht – schichtenkonform und bricht den Build *nicht*. Genau
das ist der Verstoß, der in einer Hexagonal-/Clean-Struktur am ehesten passiert, weil beide
Adapter im selben Gradle-Modul liegen und die Abhängigkeit deshalb auch compiliert.

== Optionen

. *`+onionArchitecture()+`* – ArchUnits zweite Architektur-Sicht; kennt Adapter als
  *benannte, gegenseitig unbekannte* Ringe.
. *`+layeredArchitecture()+` erweitern* – `+..adapter.in..+` und `+..adapter.out..+` als zwei
  zusätzliche Schichten deklarieren; drückt dasselbe aus, aber als Stapel, in dem die beiden
  Adapter künstlich übereinander stehen.
. *Eigenes Gradle-Modul je Adapter* – vom Build erzwungen, zerlegt aber das Adapter-Modul und
  dupliziert die jOOQ-Codegen-Konfiguration.
. *Nichts tun* – der Verstoß bleibt unentdeckt.

== Entscheidung

*Option 1* – `OnionArchitectureTest` neben dem bestehenden `LayeredArchitectureTest`, eine
Regel `+rings_are_respected+`. Ringe: `+..domain..+` als _domain model_, `+..application..+`
(Ports *und* Services) als _application service_, dazu drei Adapter `rest`, `persistence`
und `bootstrap`. Option 2 wurde verworfen, weil sie die Aussage „Adapter kennen einander
nicht" in eine Reihenfolge zwingt, die es nicht gibt; Option 3, weil sie die Struktur ändern
würde, um sie zu prüfen (dasselbe Argument wie in ADR 0012).

== Konsequenzen

*Vorteile*

* Der Zugriff Adapter → Adapter bricht jetzt den Build; er war vorher unsichtbar (Nachweis
  unten).
* Die beiden Sichten sind bewusst redundant: Wo sie sich überschneiden, prüfen sie dasselbe
  zweimal – das kostet nur Laufzeit, während die Lücke Korrektheit gekostet hat.

*Nachteile*

* `+withOptionalLayers(true)+` ist nötig, weil es keinen _domain service_-Ring gibt (die
  Domäne ist reines Modell). Der Preis: Ein Ring, der durch eine Paket-Umbenennung
  versehentlich leer läuft, fällt nicht mehr auf – die leere Schale wird nicht mehr gemeldet.
* `bootstrap` ist als Adapter modelliert. Das trifft die Sache (Composition Root im äußersten
  Ring) und ist heute korrekt, weil `bootstrap` keine Kompilier-Abhängigkeit auf einen anderen
  Adapter hat – Spring verdrahtet über Component-Scan. Verdrahtet dort künftig eine
  `@Bean`-Methode einen Adapter *explizit*, meldet die Regel einen Verstoß; dann ist
  `+ignoreDependency(...)+` das Mittel, nicht das Aufweichen der Regel.

== Nachweis, dass die Regel greift

Nach dem Maßstab aus ADR 0012 – eine Regel, die nie fehlschlägt, ist wertlos – gegen einen
absichtlichen Verstoß geprüft (2026-08-09). Ein temporärer Record im REST-Adapter, der den
generierten jOOQ-Code des Persistenz-Adapters anfasst:

[source,java]
----
package io.github.keymaster65.helloai.adapter.in.rest;
import io.github.keymaster65.helloai.adapter.out.persistence.jooq.Tables;
public record OnionViolationProbe(Class<Tables> tables) {
    public static String name() { return Tables.RECIPE.getName(); }
}
----

Ergebnis: `+rings_are_respected+` schlägt mit fünf Verstößen fehl (Feld, Konstruktor,
Rückgabetyp, Feldzugriff, Methodenaufruf). Entscheidend ist das Gegenstück: Die *fünf Regeln
aus `LayeredArchitectureTest` blieben dabei grün* – 6 Tests, 1 Fehler. Damit ist belegt, dass
die neue Regel eine echte Lücke schließt und nicht bloß Bestehendes wiederholt. Ohne die Probe
sind alle sechs Regeln grün.

== Nachtrag zur Bytecode-Einschränkung aus ADR 0012

ADR 0012 hält fest, dass ArchUnit Abhängigkeiten in generischen Typargumenten „teils nicht
mehr sieht". Die Fehlermeldung der Probe zeigt die Grenze genauer: Für *Felder, Parameter und
Rückgabetypen* liest ArchUnit die generische Signatur aus und meldet
`+has generic parameter type ... with type argument depending on ...+`. Unsichtbar bleiben
Typargumente nur dort, wo der Compiler sie wegwirft – etwa in lokalen Variablen. Die
Zurückhaltung aus ADR 0012 gegenüber Regeln auf Methodensignaturen bleibt damit richtig, ihre
Begründung ist aber enger zu fassen als dort formuliert.

== Regel für die Zukunft

* Wer einen Adapter hinzufügt (etwa ein Messaging-Adapter unter `+..adapter.out..+`), ergänzt
  ihn als *eigenen* `+adapter(...)+`-Ring. Ihn in einen bestehenden Ring zu schieben, wäre die
  stille Variante des Verstoßes, den diese Regel verhindern soll.
* Beide Architektur-Tests werden zusammen gepflegt. Widersprechen sie sich, ist das kein
  Anlass, einen davon zu löschen, sondern ein Hinweis, dass die Struktur unklar ist.
