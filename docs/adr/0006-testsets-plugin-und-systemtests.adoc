= 0006 – Eigener Source-Set für Systemtests via testsets-Plugin

== Status

Akzeptiert +
Datum: 2026-08-09

== Kontext

Bisher lagen alle Tests in `+src/test/java+` und liefen gemeinsam über `+gradle test+` –
Unit-, Property-, Web-Slice- und Integrationstests. Mit der OpenAPI-/Swagger-Oberfläche
(link:0005-springdoc-openapi-und-swagger-ui{adrext}[ADR 0005]) kommt eine Testart dazu, die
sich grundlegend anders verhält: *Systemtests*, die die *laufende Anwendung* ausschließlich
über HTTP prüfen. Sie sind langsamer (die Anwendung muss hochfahren), brauchen eine
Datenbank und sollen den schnellen `+gradle test+`-Zyklus nicht ausbremsen. Außerdem müssen
dieselben Tests gegen eine *deployte* Instanz laufen können.

== Optionen

. *`+unbroken-dome/gradle-testsets-plugin+`* (`+org.unbroken-dome.test-sets+`): deklariert
  mit `+testSets { systemtest }+` in einer Zeile Source-Set, Configurations
  (`+systemtestImplementation+`, …) und Task.
. *Gradles eingebautes `+jvm-test-suite+`*: seit Gradle 7.3 an Bord, deckt denselben Zweck
  ab, ist aber geschwätziger und die Test-Suite-DSL ist teilweise noch incubating.
. *Source-Set von Hand* in `+build.gradle+` (Source-Set + Configurations + `Test`-Task
  manuell verdrahten).
. *Alles in `+src/test+`* lassen und Systemtests per JUnit-Tag oder Namenskonvention filtern.

== Entscheidung

*Option 1 – `+org.unbroken-dome.test-sets+` in Version 4.1.0*, wie angefordert. Damit
entsteht das Source-Set `+src/systemtest/java+` und der Task *`+gradle systemtest+`*. Die
Systemtests sprechen die Anwendung nur über HTTP an (JDK-`HttpClient`); Einstiegspunkt ist
`RunningApplication` mit zwei Betriebsarten: *extern* – mit
`+-Psystemtest.baseUrl=http://host:port+` läuft die Suite gegen eine bereits
laufende/deployte Instanz; *selbst-gehostet* (Default) – die Anwendung wird einmalig auf
einem freien Port gegen ein embedded PostgreSQL gestartet
(link:0002-embedded-postgres-statt-testcontainers{adrext}[ADR 0002]), damit
`+gradle systemtest+` ohne externe Infrastruktur funktioniert. Der Task ist *bewusst nicht*
an `check`/`build` gehängt, sondern wird als eigener Schritt in der Definition of Done
geführt.

== Konsequenzen

*Vorteile*

* Klare Trennung: `+gradle test+` bleibt schnell, `+gradle systemtest+` prüft das
  Gesamtsystem.
* Systemtests kennen keine Spring-Internas, nur HTTP – sie sind damit unverändert gegen jede
  Umgebung einsetzbar (lokal, Stage, Prod-Smoke).
* Der Contract wird gegen die *Realität* geprüft, nicht nur gegen sich selbst: dokumentierte
  Statuscodes werden mit dem tatsächlichen Verhalten abgeglichen, und der
  Swagger-UI-`configUrl` wird verifiziert (sonst würde die UI die Petstore-Demo des WebJars
  rendern).

*Nachteile*

* Das Plugin ist *wenig gepflegt*: letzter Release 4.1.0 (September 2023), und Gradle liefert
  mit `+jvm-test-suite+` inzwischen einen eingebauten Ersatz. Mit *Gradle 9.6.1 wurde 4.1.0
  verifiziert* (Task wird angelegt, Source-Set kompiliert, Tests laufen); bricht ein künftiges
  Gradle-Update das Plugin, ist die Migration auf `+jvm-test-suite+` der vorgesehene Ausweg –
  die Testklassen selbst bleiben davon unberührt, nur `+build.gradle+` ändert sich.
* Ein selbst-gehosteter Lauf dauert ~45 s statt ~20 s gegen eine laufende Instanz, weil die
  Anwendung hochfährt.
* Beim Selbst-Hosting müssen Port und Datenquelle als *Command-Line-Argumente* gesetzt
  werden, nicht über `+SpringApplicationBuilder.properties(...)+`: letztere landen in
  `defaultProperties` und werden von `+application.yml+` (`+server.port: 80+`) überstimmt.

== Regel für die Zukunft

* Systemtests gehören nach `+src/systemtest/java+` und dürfen *ausschließlich* über HTTP auf
  die Anwendung zugreifen – kein `@SpringBootTest`-Zugriff auf Beans, kein direkter
  DB-Zugriff. Nur so bleiben sie gegen eine deployte Instanz lauffähig.
* `+gradle systemtest+` ist Teil der *Definition of Done* (siehe `+CLAUDE.md+`).
* Gegen eine laufende Instanz:
  `+gradle systemtest -Psystemtest.baseUrl=http://localhost:8080+`.
