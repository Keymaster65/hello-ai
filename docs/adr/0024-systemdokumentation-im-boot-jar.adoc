= ADR 0024: Systemdokumentation im Boot-Jar unter `/recipes/docs/`

== Status

Akzeptiert – 2026-08-11

== Kontext

Die Systemdokumentation liegt als AsciiDoc unter `+docs/system+` und wird von
`+./gradlew asciidoctor+` nach `+build/docs/asciidoc/system.html+` gerendert
(link:0022-asciidoc-systemdokumentation-in-docs-system{adrext}[ADR 0022]). Lesen kann sie
damit, wer das Repository ausgecheckt hat und den Build ausgeführt hat – also der Entwickler
an seiner Maschine.

Wer die _laufende_ Anwendung vor sich hat, hat das nicht. Für ihn gilt bisher: Die API
beschreibt sich selbst (Swagger UI unter `+/recipes/swagger-ui.html+`, OpenAPI unter
`+/recipes/v3/api-docs+`, link:0005-springdoc-openapi-und-swagger-ui{adrext}[ADR 0005]), die
Zusammenhänge dahinter – Bausteine, Datenmodell, Fehlerbilder, Betrieb, Teststufen und die
bewusst offenen Punkte – stehen nur im Repository. Genau die Fragen, die beim Betrieb
auftauchen, beantwortet die Instanz nicht, die vor einem läuft.

Das Frontend zeigt, wie das Projekt solche Fälle löst: Ein Deployable, eine Origin
(link:0007-react-frontend-mit-backend-als-bff{adrext}[ADR 0007]). Das Boot-Jar trägt die SPA
bereits im Klassenpfad unter `+static/+`; ein zweites Artefakt für die Dokumentation stünde
dieser Linie entgegen.

Ein Detail steht dem entgegen und ist der eigentliche Inhalt dieser Entscheidung: Das
gerenderte HTML war bisher *nicht ortsunabhängig*. Die Kapitel verlinken die ADRs über das
Attribut `+{adr}+`, das der Build auf `+../../../docs/adr+` umbog – ein Pfad, der nur von
`+build/docs/asciidoc/+` aus ins Repository trifft. ADR 0022 hat das als Nachteil
festgehalten: „Wird das HTML woandershin kopiert, brechen diese Links." Beim Ausliefern wird
genau das getan.

== Optionen

. *Nichts ausliefern.* Kostenlos. Die laufende Anwendung bleibt für alles jenseits der API
  stumm; wer sie betreibt, braucht das Repository.
. *HTML ausliefern, ADR-Links auf GitHub zeigen lassen* (`+{adr}+` =
  `+https://github.com/Keymaster65/hello-ai/blob/main/docs/adr+`). Ein Attributwert, keine
  weiteren Dateien im Jar, und GitHub rendert das Markdown lesbar. Dafür braucht die
  Dokumentation der Instanz einen Netzzugang und ein öffentliches Repository, und die
  Repository-URL steht ab dann im Buildskript – eine Kopplung, die es bisher nicht gibt.
  Zeigen die Links auf `main`, beschreiben sie außerdem nicht den ausgelieferten Stand.
. *HTML ausliefern, ADRs mit ausliefern* und die Links relativ lassen. Das Ergebnis ist in
  sich geschlossen und funktioniert ohne Netz; der Browser zeigt eine `+.md+`-Datei
  allerdings als Rohtext an oder lädt sie herunter, statt sie zu rendern.
. *ADRs beim Rendern nach HTML mitkonvertieren.* Löst die Darstellung, verlangt aber einen
  zweiten Konverter für Markdown und macht aus 23 Quelldateien 23 weitere Ergebnisse.
. *Dokumentation in die SPA einbetten* (eigene Route, Inhalt im Bundle). Bindet die
  Dokumentation an das Frontend, obwohl sie das System beschreibt und nicht die Oberfläche –
  und der Build müsste HTML in den Vite-Build reichen.

== Entscheidung

*Option 3: Das gerenderte HTML wird mit den ADRs zusammen ins Boot-Jar gepackt und unter
`+/recipes/docs/+` ausgeliefert.*

Drei Teile:

*1. Das Renderergebnis wird in sich geschlossen.* Der `asciidoctor`-Task kopiert
`+docs/adr/*.md+` in einen Ordner `+adr/+` neben das HTML, das Attribut `+{adr}+` zeigt nur
noch dorthin:

[source,kotlin]
----
resources {
    from(file("docs/adr")) { include("*.md") }
    into("adr")
}
attributes(mapOf("adr" to "adr", "attribute-missing" to "warn"))
----

Damit gilt der Nachteil aus ADR 0022 nicht mehr: Das Ausgabeverzeichnis ist als Ganzes
kopierbar. Das nützt auch lokal – `+build/docs/asciidoc/+` lässt sich weiterreichen, ohne dass
die Verweise ins Leere zeigen.

*2. Das Einpacken hängt am Modul `:bootstrap`*, wie beim Frontend, weil dort das Deployable
entsteht:

[source,kotlin]
----
from(rootProject.layout.buildDirectory.dir("docs/asciidoc")) {
    into("static/docs")
    rename("""system\.html""", "index.html")
}
----

Der Task des Wurzelprojekts rendert, das Modul packt ein – dieselbe Rollenteilung wie
`frontendBuild` → `processResources`. `-PskipDocs` überspringt den Schritt und hält die
schnelle Java-Schleife schnell, analog zu `-PskipFrontend`.

*3. `+/recipes/docs/+` ist die Adresse, nicht `+/recipes/docs/index.html+`.* Spring Boot kennt
eine Verzeichnis-Startseite nur für die Wurzel der Anwendung; `+/docs/+` liefe sonst in einen
404. `DocumentationRoutingConfig` schließt die Lücke mit zwei View-Controllern – ohne
Handler-Methode und damit auch ohne Eintrag im OpenAPI-Contract:

[source,java]
----
registry.addRedirectViewController("/docs", "/docs/");
registry.addViewController("/docs/").setViewName("forward:/docs/index.html");
----

Der abschließende Schrägstrich ist kein Schönheitsfehler, sondern die Bedingung dafür, dass
die relativen Verweise `+adr/…+` im Browser auf `+/recipes/docs/adr/…+` zeigen und nicht eine
Ebene zu hoch landen. Deshalb _leitet_ `+/docs+` um, statt weiterzuleiten.

*4. `+.md+` wird als `+text/plain;charset=UTF-8+` ausgeliefert.* Ohne Zuordnung kennt kein
Beteiligter die Endung, und die ADRs kämen als `+application/octet-stream+` – der Browser böte
einen Download an, statt den Text zu zeigen. Die Zuordnung steht als `MimeMappings`-Anpassung
am Webserver und nicht in der Content Negotiation: Seit Spring Framework 7 nimmt der
Resource-Handler seine Medientypen nicht mehr von dort (nachgemessen – die naheliegende
Variante `configureContentNegotiation` blieb wirkungslos).

*Die Auslieferung ist geprüft.* `DocumentationSystemTest` holt `+/docs/+` über HTTP, folgt
_jedem_ ADR-Verweis des Dokuments und prüft die Antwort. Ein ADR, das im Jar fehlt, während
die Doku darauf verweist, ist damit ein roter Systemtest und kein toter Link im Betrieb.

== Konsequenzen

*Vorteile*

* Die laufende Anwendung beschreibt sich vollständig: API über Swagger UI, System über
  `+/recipes/docs/+`. Ein Deployable, eine Origin – wie beim Frontend.
* Das Renderergebnis ist ortsunabhängig geworden. Der in ADR 0022 notierte Nachteil („wird das
  HTML woandershin kopiert, brechen diese Links") ist damit erledigt.
* Kein Netzzugang nötig: Die ausgelieferte Dokumentation ist vollständig, auch in einem
  abgeschotteten Netz.
* Die Dokumentation im Jar entspricht dem Stand, aus dem das Jar gebaut wurde – nicht dem
  Stand eines Branches irgendwo.
* Der Systemtest prüft die Auslieferung samt aller ADR-Verweise; sie kann nicht still
  verfallen.

*Nachteile*

* Der Browser _rendert_ die ADRs nicht: Er zeigt Markdown-Rohtext. Lesbar ist es, schön ist es
  nicht. Option 4 (Markdown mitkonvertieren) bleibt der Ausweg, wenn das stört.
* Die MIME-Zuordnung gilt für den ganzen Server, nicht nur für `+/docs/**+`. Bei genau einer
  Sorte `+.md+`-Dateien im Artefakt ist das kein Unterschied – ein zweiter Verwendungszweck
  für `+.md+` würde ihn machen.
* Das Jar wächst um die Dokumentation – Größenordnung einige hundert Kilobyte, davon der
  größte Teil das HTML mit dem eingebundenen Quellcode-Anhang.
* *Die Dokumentation ist damit öffentlich, sobald der Port es ist.* Sie nennt die offenen
  Punkte (keine Authentifizierung, kein HTTPS, kein Actuator) – für jemanden mit Zugriff auf
  die Instanz ist das eine Landkarte. Solange es keine Authentifizierung gibt
  (`+betrieb.adoc+`, „Offene Punkte"), gilt ohnehin, dass die Anwendung nicht offen betrieben
  wird; mit einer Authentifizierung wird `+/docs/**+` mit abzusichern sein.
* `processResources` hängt jetzt am `asciidoctor`-Task des Wurzelprojekts. Jede Änderung an
  einer Quelldatei macht die Doku veraltet – der Anhang bindet sie ein – und lässt sie vor
  `test` neu rendern. Dafür gibt es `-PskipDocs`.
* Wird ein ADR gelöscht oder umbenannt, bleibt die alte Kopie im Ausgabeverzeichnis liegen,
  bis `clean` läuft: Der Kopierschritt des Asciidoctor-Tasks räumt nicht auf. Das ausgelieferte
  Jar ist davon nicht betroffen, solange es – wie in der Definition of Done – aus
  `+clean build+` stammt.

*Bewusst nicht getan*

* *Kein Link in der Oberfläche.* Die SPA verwaltet Rezepte; die Systemdokumentation richtet
  sich an Entwicklung und Betrieb, nicht an den Nutzer. Sie ist über ihre Adresse erreichbar
  und in `+api.adoc+` und im README genannt. Ein Link im Frontend wäre eine Entscheidung über
  die Oberfläche und damit eine eigene.
* *Die Arbeitsgrundlage (`+docs/prompt+`, `asciidoctorPrompt`) wird nicht ausgeliefert.* Sie
  ist Anweisung an den Assistenten, nicht Beschreibung des Systems. Ihr Wortlaut steht ohnehin
  im Kapitel „Arbeitsgrundlage" der Systemdokumentation und wird damit mit ausgeliefert.
* *Keine Versionierung der Dokumentation* (`+/docs/1.0/…+`). Es gibt genau einen Stand: den
  des Jars.
