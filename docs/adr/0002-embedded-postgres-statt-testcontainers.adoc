= 0002 – Integrationstests mit embedded PostgreSQL statt Testcontainers

== Status

Akzeptiert (Abweichung von der ursprünglichen Auswahl) +
Datum: 2026-07-18

== Kontext

Für Integrationstests war ausdrücklich *Testcontainers* gewünscht (siehe `testing.md`).
Testcontainers benötigt eine laufende Docker-Umgebung. In der aktuellen
Entwicklungs-/CI-Umgebung ist *kein Docker verfügbar* (`docker` nicht installiert). Die
Tests sollen den vollen Stack (Flyway + jOOQ + Service) gegen ein echtes PostgreSQL prüfen
und trotzdem grün laufen.

== Optionen

. Testcontainers beibehalten – Tests laufen hier nicht (kein Docker).
. Gegen eine extern bereitgestellte PostgreSQL testen – nicht selbstständig/hermetisch.
. *Zonky embedded-postgres* – startet ein echtes PostgreSQL-Binary ohne Docker.

== Entscheidung

Option 3. `RecipeIntegrationTest` startet Zonky embedded-postgres und bindet es via
`@DynamicPropertySource` an die Datasource. Kann das native Binary nicht starten,
überspringt sich die Klasse automatisch (`+@EnabledIf("embeddedPostgresAvailable")+`),
statt den Build rot zu machen. Das Design bleibt Testcontainers-kompatibel (nur die
DB-Bereitstellung ist ausgetauscht).

== Konsequenzen

*Vorteile*

* Echte PostgreSQL-Verifikation ohne Docker; Tests laufen hermetisch und aktuell grün
  (4 Integrationstests).
* Rückkehr zu Testcontainers ist mit minimalem Aufwand möglich, sobald Docker vorhanden ist.

*Nachteile*

* Abweichung von der vereinbarten Test-Infrastruktur; leicht anderes Laufzeitverhalten als
  ein Container.
* Zonky lädt plattformspezifische Binaries (zusätzliche Test-Abhängigkeit).

*To do:* Bei Docker-Verfügbarkeit auf Testcontainers zurückwechseln oder beide Varianten per
Profil anbieten.
