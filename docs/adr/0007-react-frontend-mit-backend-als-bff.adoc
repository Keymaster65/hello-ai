= 0007 – React-Frontend mit dem Backend als BFF

== Status

Akzeptiert +
Datum: 2026-08-09

== Kontext

Zur bestehenden REST-API soll eine Web-Oberfläche entstehen. Der Tech-Stack für das Frontend
ist in `+CLAUDE.md+` gesetzt: TypeScript, Vite, Vitest, React. Die Anwendung soll das
vorhandene Spring-Boot-Backend als *Backend for Frontend* nutzen – also ein Backend, das auf
die Bedürfnisse genau dieses Clients zugeschnitten ist und ihn zugleich ausliefert.
Vorhanden und nutzbar: ein vollständiger, annotierter OpenAPI-3.1-Contract
(link:0005-springdoc-openapi-und-swagger-ui{adrext}[ADR 0005]).

== Optionen

*Verzahnung:*

. Gradle baut das Frontend und packt es ins Boot-Jar (ein Artefakt, eine Origin).
. Eigenständiges Frontend-Projekt mit separatem Deployment (CORS bzw. Reverse-Proxy nötig).
. Gradle-Multiprojekt mit `+:backend+`/`+:frontend+`.

*API-Typen:*

[loweralpha]
. aus dem OpenAPI-Contract generiert,
. handgeschrieben.

*Routing:*

[lowerroman]
. `react-router` mit SPA-Fallback im Backend,
. Ansichtswechsel über Komponenten-State.

== Entscheidung

*Option 1 + a + ii.* Das Frontend liegt in `+frontend/+`; Gradle-Tasks `npmInstall`,
`frontendBuild` und `frontendTest` binden npm ein, `processResources` kopiert
`+frontend/dist+` nach `+static/+` ins Boot-Jar. Damit liefert Spring Boot die SPA unter
`+/+` und die API unter `+/api+` aus *derselben Origin* – keine CORS-Konfiguration, ein
Deployable. Im Dev-Betrieb proxyt der Vite-Server (`+:5173+`) `+/api+`, `+/v3+` und
`+/swagger-ui+` auf `+:8080+`, sodass der Anwendungscode in beiden Modi identisch bleibt und
nur relative Pfade kennt. Die TypeScript-Typen erzeugt `openapi-typescript` aus
`+/v3/api-docs+` nach `+src/api/schema.d.ts+` (`+npm run generate:api+`); die Datei wird
*eingecheckt*, damit der Gradle-Build kein laufendes Backend braucht. Auf einen Router wird
verzichtet: Die Ansicht (Liste/Detail/Formular) ist Komponenten-State, wodurch das Backend
keinen SPA-Fallback für Deep-Links braucht. Ein `-PskipFrontend` hält die reine
Java-Schleife schnell.

== Konsequenzen

*Vorteile*

* Ein Artefakt, eine Origin: kein CORS, kein zweites Deployment, keine Origin-Konfiguration
  im Code.
* Der Contract ist Single Source of Truth bis in die UI: Ändert das Backend ein Feld, bricht
  `tsc` im Build – nicht erst der Browser zur Laufzeit. Genau dadurch fiel auf, dass die
  *Response-DTOs im Contract zunächst keine Pflichtfelder markierten* (springdoc leitet
  `required` nur aus Bean-Validation ab, die auf Responses nicht greift). Behoben mit
  `+@Schema(requiredMode = REQUIRED)+` an den vom Domänenmodell garantierten Feldern; echte
  Nullable-Felder bleiben bewusst optional, damit der Contract nicht mehr verspricht, als er
  hält.
* Systemtests decken das Zusammenspiel ab (`FrontendSystemTest`).

*Nachteile*

* `+gradle build+` braucht jetzt Node/npm und wird um den Frontend-Build und die
  Vitest-Suite länger; ohne Node schlägt der Build fehl (Ausweg: `-PskipFrontend`).
* Kein Router bedeutet: keine teilbaren URLs für einzelne Rezepte. Kommt `react-router` dazu,
  braucht das Backend einen Forwarding-Controller für unbekannte Pfade.
* Die generierte `+schema.d.ts+` ist eingecheckt und kann veralten; sie muss nach
  API-Änderungen mit `+npm run generate:api+` erneuert werden (bei laufendem Backend).
* `typescript` ist auf *5.9* gepinnt, obwohl 7.0 verfügbar ist: `openapi-typescript` verlangt
  derzeit `+peer typescript@^5.x+`.

== Regel für die Zukunft

* Das Frontend spricht *ausschließlich relative* `+/api+`-Pfade an – keine absolute
  Backend-URL, keine Origin aus der Umgebung. Das ist die Bedingung dafür, dass Dev-Proxy und
  Produktionsauslieferung denselben Code tragen.
* Nach jeder Änderung an der API: `+npm run generate:api+` gegen ein laufendes Backend und die
  aktualisierte `+src/api/schema.d.ts+` mit einchecken.
* Neue API-Typen werden *nicht* von Hand in TypeScript nachgebaut, sondern aus dem Contract
  abgeleitet.
