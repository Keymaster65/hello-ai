= Build und Betrieb

== Build

Gebaut wird ausschließlich über den Gradle-Wrapper
(link:{adr}/0009-gradle-wrapper-verbindlich{adrext}[ADR 0009]), Buildskripte im Kotlin-DSL
(link:{adr}/0010-gradle-kotlin-dsl{adrext}[ADR 0010]). Alle Koordinaten und Versionen stehen in
<<src-libs-versions,`gradle/libs.versions.toml`>> (link:{adr}/0018-versionskatalog-libs-versions-toml{adrext}[ADR 0018]).

[cols="2,3", options="header"]
|===
| Befehl | Wirkung

| `./gradlew clean build`
| Frontend und Backend, alle Java- und Vitest-Tests, JaCoCo-Report, Boot-Jar,
  gerenderte Systemdokumentation.
| `./gradlew test`
| Nur die Java-Tests, danach der JaCoCo-Report.
| `./gradlew frontendTest`
| Nur Vitest.
| `./gradlew systemtest`
| Black-Box-Tests über HTTP gegen die laufende Anwendung.
| `./gradlew e2eTest`
| Playwright im echten Browser gegen das Boot-Jar. Braucht eine erreichbare PostgreSQL.
| `./gradlew asciidoctor`
| Rendert `docs/system/system.adoc` nach `build/docs/asciidoc/system.html` und legt die ADRs
  als `adr/` daneben. Enthaltene PlantUML-Diagramme werden dabei aus ihrer Quelle im Dokument
  zu SVG-Dateien neben dem HTML (link:{adr}/0042-plantuml-fuer-diagramme{adrext}[ADR 0042]).
  Das Ergebnis wandert von dort ins Boot-Jar
  (link:{adr}/0024-systemdokumentation-im-boot-jar{adrext}[ADR 0024]); ausgenommen ist der
  Diagramm-Cache `.asciidoctor/`, der zum Bauen gehört. In das HTML kopiert wird außerdem
  `docs/system/docinfo-footer.html`, das Beiwerk des klappbaren Inhaltsverzeichnisses
  (link:{adr}/0043-inhaltsverzeichnis-klappbar-per-docinfo{adrext}[ADR 0043]) – als
  Nicht-AsciiDoc-Datei ist sie im Buildskript *einzeln* als Eingabe angemeldet.
| `./gradlew asciidoctorAdr`
| Rendert `docs/adr/*.adoc` nach `build/docs/adr/`. Hängt am Task darüber, der das Ergebnis
  neben die Systemdokumentation kopiert
  (link:{adr}/0026-adrs-als-asciidoc{adrext}[ADR 0026]).
| `./gradlew gitChangelog`
| Schreibt die git-Historie als Tabelle nach `build/docs/changelog/gitchangelog.adoc`, die der
  Anhang <<git-historie>> einbindet. Hängt am `asciidoctor`-Task darüber und läuft *immer*, nie
  „up-to-date" (link:{adr}/0036-git-historie-als-erzeugtes-kapitel{adrext}[ADR 0036]).
| `./gradlew coverageTable`
| Misst die Abdeckung – er stößt den `test`-Lauf jedes Backend-Moduls an – und schreibt sie als
  Tabelle nach `docs/system/abdeckung-tabelle.adoc`, die das Kapitel <<abdeckung-tabelle>>
  einbindet (link:{adr}/0047-testabdeckung-als-eingecheckte-tabelle{adrext}[ADR 0047]). Hängt an
  keinem anderen Task: Das Ergebnis ist eingecheckt und wird ausdrücklich nachgezogen.
| `./gradlew asciidoctorPrompt`
| Rendert `docs/prompt/prompt.adoc` – Master-Prompt und Skills – nach
  `build/docs/prompt/prompt.html`
  (link:{adr}/0023-asciidoc-fuer-masterprompt-und-skills{adrext}[ADR 0023]).
| `./gradlew bootRun`
| Startet die Anwendung. Braucht eine erreichbare PostgreSQL.
| `./gradlew build -PskipFrontend`
| Überspringt npm-Installation, Vite-Build und Vitest – die schnelle Java-Schleife, auch
  auf Maschinen ohne Node.
| `./gradlew build -PskipDocs`
| Überspringt das Einpacken der Systemdokumentation und damit das Rendern vor jedem `test`.
  Das Jar enthält dann *keine* Dokumentation – `DocumentationSystemTest` schlägt fehl, und der
  MCP-Server bietet weder Dokumentationsseiten noch Ressourcen an
  (link:{adr}/0049-mcp-service-fuer-rezepte-und-dokumentation{adrext}[ADR 0049]).
|===

Die Befehle funktionieren unverändert auf jeder Ebene, weil Gradle einen Task-Namen an jedes
Projekt weiterleitet, das ihn kennt. Die Buildskripte selbst stehen in <<src-gruppe-build>>.

=== Wie das Deployable entsteht

.Was in das Boot-Jar fließt und wer es zusammensetzt
[plantuml,deployable,svg]
....
@startuml
!pragma layout smetana
skinparam shadowing false
skinparam componentStyle rectangle

file "db/changelog/\ndb.changelog-master.xml" as changelog
folder "modules/frontend" as frontend
folder "docs/system" as docsrc

component ":adapter" as adapter
component ":bootstrap" as bootstrap
artifact "recipes-<version>.jar" as jar

changelog --> adapter : jOOQ-Codegen,\nohne laufende Datenbank
adapter --> bootstrap : Klassen der Schichtmodule
frontend --> bootstrap : npmInstall, frontendBuild\n(tsc --noEmit && vite build) → dist/
docsrc --> bootstrap : asciidoctor → build/docs/asciidoc
bootstrap --> jar : processResources: dist/ → static/,\nDoku → static/docs/; dann bootJar
@enduml
....

Der Frontend-Build hängt am Modul `:bootstrap`, weil dort das Deployable zusammengesetzt
wird. Spring Boot liefert das Bundle anschließend aus dem Klassenpfad aus – SPA und API
kommen aus derselben Origin
(link:{adr}/0007-react-frontend-mit-backend-als-bff{adrext}[ADR 0007]).

Dieselbe Rollenteilung gilt für die Systemdokumentation: Gerendert wird sie im
Wurzelprojekt (`asciidoctor`), eingepackt in `:bootstrap`. Beim Kopieren wird `system.html`
zu `index.html`, die mitkopierten ADRs behalten ihren Ordner. Ausgeliefert wird das unter
`/recipes/docs/`
(link:{adr}/0024-systemdokumentation-im-boot-jar{adrext}[ADR 0024]) – die Anwendung trägt ihre
Beschreibung damit bei sich.

Zwei Eigenschaften, die im Alltag zählen:

* *Der Build braucht keine Datenbank.* Die jOOQ-Codegenerierung interpretiert das
  Liquibase-Changelog im Speicher, die Integrationstests nutzen embedded PostgreSQL
  (link:{adr}/0002-embedded-postgres-statt-testcontainers{adrext}[ADR 0002]).
* *Der Artefaktname ist vom Modulnamen entkoppelt*: `recipes-<version>.jar`, nicht
  `bootstrap-<version>.jar` (link:{adr}/0011-backend-als-gradle-modul{adrext}[ADR 0011]).

== Konfiguration

Konfiguriert wird über Umgebungsvariablen; <<src-application-yml,`application.yml`>> enthält
nur Defaults für die
lokale Entwicklung. Es gibt bewusst keine Profil-Dateien je Umgebung.

[cols="2,2,3", options="header"]
|===
| Variable | Default | Bedeutung

| `DB_URL`
| `jdbc:postgresql://localhost:5432/recipes`
| JDBC-URL der Datenbank

| `DB_USERNAME`
| `recipes`
| Datenbankbenutzer

| `DB_PASSWORD`
| `recipes`
| Passwort. In einer echten Umgebung zwingend zu setzen – der Default ist ein
  Entwicklungswert.

| `SPRING_LIQUIBASE_CONTEXTS`
| _(nicht gesetzt)_
| Ohne Angabe laufen alle Changesets inklusive Beispieldaten. Mit `prod` bleibt das
  Seed-Changeset aus.

| `SERVER_PORT`
| `80`
| HTTP-Port. Der Default aus `application.yml` ist `80`; Entwicklung und E2E-Tests nutzen
  üblicherweise `8080` (`--server.port=8080`).

| `RECIPES_GITDATA_ENABLED`
| `false`
| Schaltet die zweite Ablage ein: den git-Store *und* seine Adresse
  `+/api/gitdata/recipes+` (link:{adr}/0054-zweite-rest-front-auf-dem-gitdata-store{adrext}[ADR
  0054]). Ohne sie gibt es beides nicht.

| `RECIPES_GITDATA_REPOSITORY`
| _(nicht gesetzt)_
| Verzeichnis des Repositories, in das der Store schreibt; beim Start als *bare* Repository
  angelegt, wenn dort keines liegt. Zwingend, sobald eingeschaltet – ein Vorgabewert wäre ein
  Verzeichnis, in dem jemand anders arbeitet.

| `RECIPES_GITDATA_BRANCH`
| `data`
| Branch, auf dem die Zeilen liegen. Er entsteht mit dem ersten Commit und ist wurzellos
  (link:{adr}/0053-gitdata-adapter-rezepte-als-json-im-branch-data{adrext}[ADR 0053]).

| `SECURITY_TXT_CONTACT`
| `https://github.com/Keymaster65/hello-ai/issues`
| Meldeweg für Schwachstellen, ausgeliefert unter `+/.well-known/security.txt+` (RFC 9116).
  Mehrere URIs kommagetrennt, die bevorzugte zuerst
  (link:{adr}/0037-security-txt-am-ursprung-per-engine-valve{adrext}[ADR 0037]).

| `SECURITY_TXT_EXPIRES`
| `2027-08-01T00:00:00Z`
| Ablaufdatum derselben Datei nach RFC 3339. Ein unlesbarer Wert bricht den *Start*; ein
  abgelaufener oder mehr als ein Jahr entferntes Datum bricht den *Build*
  (`SecurityTxtConfigurationTest`).
|===

Feste Festlegungen, die *nicht* über Umgebungsvariablen wandern sollten, ohne beide Seiten
anzupassen:

[cols="2,3", options="header"]
|===
| Festlegung | Wer sie außerdem kennt

| Context-Path `/recipes`
| <<src-vite-config,`vite.config.ts`>> (`base`),
  <<src-playwright-config,`playwright.config.ts`>> (`CONTEXT_PATH`), der `basename` der
  SPA. Eine Änderung betrifft alle drei
  (link:{adr}/0016-context-path-recipes{adrext}[ADR 0016]).

| Liquibase aktiv, Changelog-Pfad
| Die jOOQ-Codegenerierung liest dieselbe Datei; ein Umzug betrifft
  <<src-build-gradle-adapter,`modules/backend/adapter/build.gradle.kts`>>.

| SQL-Dialekt `POSTGRES`
| Die generierten jOOQ-Klassen. Ein anderer Dialekt bedeutet Neugenerierung.

| `+spring.mvc.problemdetails.enabled: true+`
| Ohne den Schalter fallen `405`, `415` und ihresgleichen wieder auf die Standardseite zurück,
  während die vier eigenen Fälle weiter `+application/problem+json+` liefern – zwei
  Fehlerbilder statt einem
  (link:{adr}/0046-rfc-9457-problem-details-als-fehlerformat{adrext}[ADR 0046]).
|===

== Laufzeitumgebung

Ein einzelner Prozess, eine Datenbank – kein Cluster, kein Cache, keine Queue.

[cols="1,1,3", options="header"]
|===
| Baustein | Betriebsform | Anmerkung

| `recipes-<version>.jar`
| JVM-Prozess (`java -jar`)
| Enthält Server, API, SPA, MCP-Endpunkt und die Systemdokumentation. Java 25 zur Laufzeit.

| PostgreSQL
| eigener Dienst
| Schema wird beim Start migriert. Nicht erreichbar heißt: Der Prozess startet nicht.
|===

.Produktion – oder lokal wie in Produktion
[source,bash]
----
java -jar modules/backend/bootstrap/build/libs/recipes-*.jar    # → http://localhost/recipes/
----

.Lokale PostgreSQL
[source,bash]
----
docker run --name recipes-db -e POSTGRES_DB=recipes \
  -e POSTGRES_USER=recipes -e POSTGRES_PASSWORD=recipes \
  -p 5432:5432 -d postgres:18
----

.Entwicklung mit Hot Module Replacement
[source,bash]
----
./gradlew bootRun                          # Backend, hier üblicherweise auf :8080
cd modules/frontend && npm run dev         # → http://localhost:5173/recipes/
----

Der Vite-Dev-Server liefert die SPA unter derselben Basis `/recipes/` und proxyt nur die
Backend-Pfade (`/recipes/api`, `/recipes/v3`, `/recipes/swagger-ui`) auf `:8080` – *nicht*
`/recipes/` selbst, sonst würde der Proxy die SPA verschlucken, die Vite dort ausliefert.
Der Anwendungscode ist in beiden Modi identisch, weil er nur relative Pfade kennt.

== Start und Migration

. JVM startet, Spring Boot fährt den Kontext hoch.
. Liquibase prüft `databasechangelog` und führt fehlende Changesets aus – gefiltert nach
  `SPRING_LIQUIBASE_CONTEXTS`.
. jOOQ erhält seinen `DSLContext` auf der konfigurierten `DataSource`.
. Der Katalog der Dokumentationsseiten wird vom Klassenpfad gelesen – einmalig, weil die
  ausgelieferte Dokumentation sich zur Laufzeit nicht ändert
  (link:{adr}/0049-mcp-service-fuer-rezepte-und-dokumentation{adrext}[ADR 0049]).
. *Nur mit `RECIPES_GITDATA_ENABLED`:* Das Repository wird geöffnet – als bare Repository
  angelegt, wenn dort keines liegt – und, falls der Branch *noch nicht existiert*, mit denselben
  sechs Rezepten befüllt, die auch das Seed-Changeset einfügt: ein Commit je Rezept
  (link:{adr}/0055-anfangspopulation-des-gitdata-stores-aus-dem-seed-changeset{adrext}[ADR 0055]).
  Ein vorhandener Branch bleibt unangetastet, auch ein leerer. Das geschieht *vor* dem nächsten
  Schritt: Kein Aufruf trifft auf einen halb befüllten Bestand.
. Der HTTP-Port wird geöffnet; SPA, API, MCP-Endpunkt, Swagger UI und Systemdokumentation sind
  erreichbar –
  dazu, als einziger Pfad *neben* dem Context-Path, `+/.well-known/security.txt+`
  (link:{adr}/0037-security-txt-am-ursprung-per-engine-valve{adrext}[ADR 0037]).

Ein Rollback von Changesets ist nicht vorgesehen; das Vorgehen bei einer fehlerhaften
Migration ist ein neues, korrigierendes Changeset.

[[offene-punkte]]
== Offene Punkte

Diese Punkte sind bewusst nicht umgesetzt. Sie stehen hier, damit sie nicht mit
„vergessen" verwechselt werden – und damit niemand die Anwendung in einer offenen
Umgebung betreibt, ohne sie zu kennen.

[cols="2,3", options="header"]
|===
| Fehlt | Folge

| Authentifizierung und Autorisierung
| Jeder, der den Port erreicht, kann alle Rezepte lesen, ändern und löschen – und unter
  `/recipes/docs/` diese Dokumentation samt der Liste hier lesen
  (link:{adr}/0024-systemdokumentation-im-boot-jar{adrext}[ADR 0024]). Dasselbe gilt für den
  MCP-Endpunkt `+/recipes/api/mcp+` und seine REST-Fassade unter `+/recipes/api/mcp/…+`: Sie sind
  offen erreichbar, dort allerdings *nur lesend*, und geben dieselben Rezepte und dieselbe
  Dokumentation heraus
  (link:{adr}/0049-mcp-service-fuer-rezepte-und-dokumentation{adrext}[ADR 0049],
  link:{adr}/0050-rest-facade-des-mcp-service-in-openapi{adrext}[ADR 0050]). Die Anwendung
  gehört daher hinter einen kontrollierten Zugang oder in ein privates Netz; kommt eine
  Authentifizierung, sind `/recipes/docs/**` und `+/recipes/api/mcp+` samt Fassade mit abzusichern.

| Origin-Prüfung an der REST-Fassade des MCP-Servers
| Der Protokollendpunkt weist eine Anfrage mit `Origin`-Header mit `403` ab – der Schutz gegen
  DNS-Rebinding, den die MCP-Spezifikation verlangt
  (link:{adr}/0049-mcp-service-fuer-rezepte-und-dokumentation{adrext}[ADR 0049]). Die Fassade läuft
  durch Spring MVC und an diesem Ventil vorbei; eine Seite im Browser kann sie also aufrufen
  (link:{adr}/0050-rest-facade-des-mcp-service-in-openapi{adrext}[ADR 0050]). Neue Daten gibt das
  nicht frei – `+/recipes/api/recipes+` liegt offen und sogar schreibend, `/recipes/docs/**`
  ebenso –, freigegeben wird der Weg. Ein Schutz wäre eine Festlegung für die *Anwendung*, nicht
  für diesen Pfad.

| Schutz des git-Stores, wenn er eingeschaltet ist
| Mit `RECIPES_GITDATA_ENABLED` entsteht eine *zweite schreibende* Adresse,
  `+/recipes/api/gitdata/recipes+`, und hinter ihr schreibt die Anwendung Commits in ein
  Repository auf der Platte
  (link:{adr}/0054-zweite-rest-front-auf-dem-gitdata-store{adrext}[ADR 0054]). Ohne
  Authentifizierung kann sie jeder auslösen, der den Port erreicht; wer das Repository liest,
  sieht die ganze Historie der Daten. Das Verzeichnis gehört deshalb dorthin, wo nur die
  Anwendung schreibt – *nicht* in ein Repository, in dem jemand arbeitet. Ausgeschaltet
  (Vorgabe) gibt es weder Adresse noch Repository.

| HTTPS
| Wird nicht von der Anwendung geleistet; TLS müsste ein vorgelagerter Proxy übernehmen.

| Sicherheits-Header der Auslieferung
| Die Anwendung setzt weder eine Content Security Policy noch `X-Content-Type-Options`,
  `Referrer-Policy` oder `X-Frame-Options`. Die SPA bleibt damit ohne die zweite Linie, die ein
  eingeschleustes Skript oder ein fremder Rahmen sonst fände – der Schutz hängt allein
  daran, dass React alles maskiert, was es rendert
  (`docs/prompt/security-frontend.adoc`).

| Health- und Metrik-Endpunkte
| Kein Actuator eingebunden. Für eine Bereitschaftsprüfung dient derzeit nur
  `GET /recipes/api/recipes` – das ist der Weg, den auch die E2E-Suite nutzt, um auf die
  Startbereitschaft zu warten.

| Strukturierte Protokollierung, Tracing
| Es gilt die Spring-Boot-Voreinstellung. Es gibt keine Korrelations-IDs.

| Rate Limiting, Paginierung
| `GET /api/recipes` liefert *alle* Rezepte in einer Antwort, und das Werkzeug `+list_recipes+`
  des MCP-Servers tut dasselbe. Bei großen Beständen wächst die Antwort unbegrenzt.

| Zielumgebung, CI-Pipeline, Container-Image
| Es gibt kein Deployment-Artefakt jenseits des Boot-Jars und keine automatisierte
  Auslieferung.

| Vertraulicher Meldeweg für Schwachstellen
| Die `security.txt` ist da (link:{adr}/0037-security-txt-am-ursprung-per-engine-valve{adrext}[ADR
  0037]), ihr `Contact` zeigt aber auf die *öffentlichen* Issues des Repositories. Wer eine
  Schwachstelle meldet, macht sie damit im selben Moment bekannt. Ein privater Kanal – etwa
  GitHub Security Advisories oder eine gepflegte Adresse – steht als Vorschlag im Backlog.

| Signatur der `security.txt`
| RFC 9116 erlaubt eine Clearsign-Signatur samt `Signature`-Feld. Sie fehlt: Ohne sie ist der
  Inhalt der Datei nicht als echt nachweisbar. Ein gepflegter Schlüssel ist eine eigene
  Entscheidung (link:{adr}/0035-security-skill-und-security-txt{adrext}[ADR 0035]).

| Prüfbedingung auf `difficulty`
| Die Spalte ist ein `VARCHAR` ohne `CHECK`. Ein per Hand eingefügter Fremdwert fällt erst
  beim Lesen auf – dann als Fehler in der Anwendung.
|===
