= Build und Betrieb

== Build

Gebaut wird ausschließlich über den Gradle-Wrapper
(link:{adr}/0009-gradle-wrapper-verbindlich.md[ADR 0009]), Buildskripte im Kotlin-DSL
(link:{adr}/0010-gradle-kotlin-dsl.md[ADR 0010]). Alle Koordinaten und Versionen stehen in
<<src-libs-versions,`gradle/libs.versions.toml`>> (link:{adr}/0018-versionskatalog-libs-versions-toml.md[ADR 0018]).

[cols="2,3", options="header"]
|===
| Befehl | Wirkung

| `./gradlew clean build`
| Frontend und Backend, alle Java- und Vitest-Tests, JaCoCo-Report, Boot-Jar,
  gerenderte Systemdokumentation.
| `./gradlew test`
| Nur die Java-Tests, danach der JaCoCo-Report.
| `./gradlew frontendTest`
| Nur Vitest.
| `./gradlew systemtest`
| Black-Box-Tests über HTTP gegen die laufende Anwendung.
| `./gradlew e2eTest`
| Playwright im echten Browser gegen das Boot-Jar. Braucht eine erreichbare PostgreSQL.
| `./gradlew asciidoctor`
| Rendert `docs/system/system.adoc` nach `build/docs/asciidoc/system.html` und legt die ADRs
  als `adr/` daneben. Das Ergebnis wandert von dort ins Boot-Jar
  (link:{adr}/0024-systemdokumentation-im-boot-jar.md[ADR 0024]).
| `./gradlew asciidoctorPrompt`
| Rendert `docs/prompt/prompt.adoc` – Master-Prompt und Skills – nach
  `build/docs/prompt/prompt.html`
  (link:{adr}/0023-asciidoc-fuer-masterprompt-und-skills.md[ADR 0023]).
| `./gradlew bootRun`
| Startet die Anwendung. Braucht eine erreichbare PostgreSQL.
| `./gradlew build -PskipFrontend`
| Überspringt npm-Installation, Vite-Build und Vitest – die schnelle Java-Schleife, auch
  auf Maschinen ohne Node.
| `./gradlew build -PskipDocs`
| Überspringt das Einpacken der Systemdokumentation und damit das Rendern vor jedem `test`.
  Das Jar enthält dann *keine* Dokumentation – `DocumentationSystemTest` schlägt fehl.
|===

Die Befehle funktionieren unverändert auf jeder Ebene, weil Gradle einen Task-Namen an jedes
Projekt weiterleitet, das ihn kennt. Die Buildskripte selbst stehen in <<src-gruppe-build>>.

=== Wie das Deployable entsteht

----
:domain → :application → :adapter → :bootstrap
                            │            │
                 jOOQ-Codegen aus        ├── processResources ← modules/frontend/dist  → static/
                 dem Changelog           │                    ← build/docs/asciidoc    → static/docs/
                                         └── bootJar
                                              → modules/backend/bootstrap/build/libs/recipes-<version>.jar
----

Der Frontend-Build hängt am Modul `:bootstrap`, weil dort das Deployable zusammengesetzt
wird: `npmInstall` → `frontendBuild` (`tsc --noEmit && vite build`) →
`processResources` legt `dist/` nach `static/` in das Jar. Spring Boot liefert das Bundle
anschließend aus dem Klassenpfad aus – SPA und API kommen aus derselben Origin
(link:{adr}/0007-react-frontend-mit-backend-als-bff.md[ADR 0007]).

Dieselbe Rollenteilung gilt für die Systemdokumentation: Gerendert wird sie im
Wurzelprojekt (`asciidoctor`), eingepackt in `:bootstrap`. `processResources` kopiert
`build/docs/asciidoc/` nach `static/docs/`; dabei wird `system.html` zu `index.html`, die
mitkopierten ADRs behalten ihren Ordner. Ausgeliefert wird das unter `/recipes/docs/`
(link:{adr}/0024-systemdokumentation-im-boot-jar.md[ADR 0024]) – die Anwendung trägt ihre
Beschreibung damit bei sich.

Zwei Eigenschaften, die im Alltag zählen:

* *Der Build braucht keine Datenbank.* Die jOOQ-Codegenerierung interpretiert das
  Liquibase-Changelog im Speicher, die Integrationstests nutzen embedded PostgreSQL
  (link:{adr}/0002-embedded-postgres-statt-testcontainers.md[ADR 0002]).
* *Der Artefaktname ist vom Modulnamen entkoppelt*: `recipes-<version>.jar`, nicht
  `bootstrap-<version>.jar` (link:{adr}/0011-backend-als-gradle-modul.md[ADR 0011]).

== Konfiguration

Konfiguriert wird über Umgebungsvariablen; <<src-application-yml,`application.yml`>> enthält
nur Defaults für die
lokale Entwicklung. Es gibt bewusst keine Profil-Dateien je Umgebung.

[cols="2,2,3", options="header"]
|===
| Variable | Default | Bedeutung

| `DB_URL`
| `jdbc:postgresql://localhost:5432/recipes`
| JDBC-URL der Datenbank

| `DB_USERNAME`
| `recipes`
| Datenbankbenutzer

| `DB_PASSWORD`
| `recipes`
| Passwort. In einer echten Umgebung zwingend zu setzen – der Default ist ein
  Entwicklungswert.

| `SPRING_LIQUIBASE_CONTEXTS`
| _(nicht gesetzt)_
| Ohne Angabe laufen alle Changesets inklusive Beispieldaten. Mit `prod` bleibt das
  Seed-Changeset aus.

| `SERVER_PORT`
| `80`
| HTTP-Port. Der Default aus `application.yml` ist `80`; Entwicklung und E2E-Tests nutzen
  üblicherweise `8080` (`--server.port=8080`).
|===

Feste Festlegungen, die *nicht* über Umgebungsvariablen wandern sollten, ohne beide Seiten
anzupassen:

[cols="2,3", options="header"]
|===
| Festlegung | Wer sie außerdem kennt

| Context-Path `/recipes`
| <<src-vite-config,`vite.config.ts`>> (`base`),
  <<src-playwright-config,`playwright.config.ts`>> (`CONTEXT_PATH`), der `basename` der
  SPA. Eine Änderung betrifft alle drei
  (link:{adr}/0016-context-path-recipes.md[ADR 0016]).

| Liquibase aktiv, Changelog-Pfad
| Die jOOQ-Codegenerierung liest dieselbe Datei; ein Umzug betrifft
  <<src-build-gradle-adapter,`modules/backend/adapter/build.gradle.kts`>>.

| SQL-Dialekt `POSTGRES`
| Die generierten jOOQ-Klassen. Ein anderer Dialekt bedeutet Neugenerierung.
|===

== Laufzeitumgebung

Ein einzelner Prozess, eine Datenbank – kein Cluster, kein Cache, keine Queue.

[cols="1,1,3", options="header"]
|===
| Baustein | Betriebsform | Anmerkung

| `recipes-<version>.jar`
| JVM-Prozess (`java -jar`)
| Enthält Server, API, SPA und die Systemdokumentation. Java 25 zur Laufzeit.

| PostgreSQL
| eigener Dienst
| Schema wird beim Start migriert. Nicht erreichbar heißt: Der Prozess startet nicht.
|===

.Produktion – oder lokal wie in Produktion
[source,bash]
----
java -jar modules/backend/bootstrap/build/libs/recipes-*.jar    # → http://localhost/recipes/
----

.Lokale PostgreSQL
[source,bash]
----
docker run --name recipes-db -e POSTGRES_DB=recipes \
  -e POSTGRES_USER=recipes -e POSTGRES_PASSWORD=recipes \
  -p 5432:5432 -d postgres:18
----

.Entwicklung mit Hot Module Replacement
[source,bash]
----
./gradlew bootRun                          # Backend, hier üblicherweise auf :8080
cd modules/frontend && npm run dev         # → http://localhost:5173/recipes/
----

Der Vite-Dev-Server liefert die SPA unter derselben Basis `/recipes/` und proxyt nur die
Backend-Pfade (`/recipes/api`, `/recipes/v3`, `/recipes/swagger-ui`) auf `:8080` – *nicht*
`/recipes/` selbst, sonst würde der Proxy die SPA verschlucken, die Vite dort ausliefert.
Der Anwendungscode ist in beiden Modi identisch, weil er nur relative Pfade kennt.

== Start und Migration

. JVM startet, Spring Boot fährt den Kontext hoch.
. Liquibase prüft `databasechangelog` und führt fehlende Changesets aus – gefiltert nach
  `SPRING_LIQUIBASE_CONTEXTS`.
. jOOQ erhält seinen `DSLContext` auf der konfigurierten `DataSource`.
. Der HTTP-Port wird geöffnet; SPA, API, Swagger UI und Systemdokumentation sind erreichbar.

Ein Rollback von Changesets ist nicht vorgesehen; das Vorgehen bei einer fehlerhaften
Migration ist ein neues, korrigierendes Changeset.

[[offene-punkte]]
== Offene Punkte

Diese Punkte sind bewusst nicht umgesetzt. Sie stehen hier, damit sie nicht mit
„vergessen" verwechselt werden – und damit niemand die Anwendung in einer offenen
Umgebung betreibt, ohne sie zu kennen.

[cols="2,3", options="header"]
|===
| Fehlt | Folge

| Authentifizierung und Autorisierung
| Jeder, der den Port erreicht, kann alle Rezepte lesen, ändern und löschen – und unter
  `/recipes/docs/` diese Dokumentation samt der Liste hier lesen
  (link:{adr}/0024-systemdokumentation-im-boot-jar.md[ADR 0024]). Die Anwendung
  gehört daher hinter einen kontrollierten Zugang oder in ein privates Netz; kommt eine
  Authentifizierung, ist `/recipes/docs/**` mit abzusichern.

| HTTPS
| Wird nicht von der Anwendung geleistet; TLS müsste ein vorgelagerter Proxy übernehmen.

| Health- und Metrik-Endpunkte
| Kein Actuator eingebunden. Für eine Bereitschaftsprüfung dient derzeit nur
  `GET /recipes/api/recipes` – das ist der Weg, den auch die E2E-Suite nutzt, um auf die
  Startbereitschaft zu warten.

| Strukturierte Protokollierung, Tracing
| Es gilt die Spring-Boot-Voreinstellung. Es gibt keine Korrelations-IDs.

| Rate Limiting, Paginierung
| `GET /api/recipes` liefert *alle* Rezepte in einer Antwort. Bei großen Beständen wächst
  die Antwort unbegrenzt.

| Zielumgebung, CI-Pipeline, Container-Image
| Es gibt kein Deployment-Artefakt jenseits des Boot-Jars und keine automatisierte
  Auslieferung.

| Prüfbedingung auf `difficulty`
| Die Spalte ist ein `VARCHAR` ohne `CHECK`. Ein per Hand eingefügter Fremdwert fällt erst
  beim Lesen auf – dann als Fehler in der Anwendung.
|===
