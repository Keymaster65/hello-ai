[[git-historie]]
= Git-Historie

Die zweite Sicht auf dieselbe Arbeit, die <<session-protokoll>> aus der Richtung des Prompts
zeigt: *was* das Repository verändert hat, ein Eintrag je Commit
(link:{adr}/0036-git-historie-als-erzeugtes-kapitel{adrext}[ADR 0036]).

Die Tabelle unten wird bei jedem Build aus der git-Historie *erzeugt* – vom Gradle-Task
`gitChangelog`. Sie liegt deshalb nicht im Repository, sondern entsteht unter `build/` und wird
von dort eingebunden: Ein Commit kann sich selbst nicht enthalten, eine eingecheckte Fassung
wäre ab ihrem Entstehen um genau einen Commit alt.

Neuester Commit oben – dieselbe Richtung wie im Protokoll, im ADR-Index und in der
Kennzahlen-Tabelle. Der Kurz-Hash benennt den Commit, der Betreff ist die *erste Zeile* seiner
Message; der Rumpf samt `Co-Authored-By`-Zeile bleibt draußen.

Der Hash in der Spalte *„Commit"* ist ein *Link auf das Diff bei GitHub*
(link:{adr}/0052-commit-hashes-als-links-auf-github{adrext}[ADR 0052]) – die eine Angabe, die
diese Tabelle nach außen führt. Die Basis-URL steht als Konstante in `build.gradle.kts`; geprüft
wird der Link nicht, ein Umzug des Repositories fällt also erst beim Klicken auf.

Die Spalte *„Nr"* zählt die Zeilen – aber *von unten*: Der `Initial commit` ist die `1`, der
jüngste Commit trägt die Anzahl der Zeilen
(link:{adr}/0051-git-historie-ohne-aussagelose-betreffe{adrext}[ADR 0051]). In dieser Richtung
*bleibt* die Nummer eines Commits: Ein neuer Commit hängt oben eine höhere Zahl an, statt alle
darunter zu verschieben. Sie ist eine Lesehilfe – „die dritte Zeile von unten" –, kein Bezeichner:
Der Commit wird über seinen Kurz-Hash benannt, und nur der steht auch im Protokoll.

Die Spalte *„Prompt"* nennt die Einträge des Protokolls, aus denen der Commit hervorgegangen
ist (link:{adr}/0038-querverweise-zwischen-prompt-und-commit{adrext}[ADR 0038]). Sie ist
*abgeleitet*: Gelesen wird allein die Zeile `+_Commit:_+` des jeweiligen Eintrags, nicht dessen
Fließtext. Ein `–` heißt deshalb nicht „kein Prompt", sondern *„kein Eintrag schreibt sich
diesen Commit zu"* – bei den Commits, die vor dieser Entscheidung entstanden sind, ist das die
Regel. In die Gegenrichtung zeigt der Anker `+commit-<kurzhash>+` jeder Zeile, auf den das
Protokoll und die Kennzahlen-Tabelle in <<kennzahlen>> verweisen
(link:{adr}/0041-kennzahlen-tabelle-verlinkt-protokoll-und-historie{adrext}[ADR 0041]).

Drei Auslassungen gehören dazugesagt, damit die Tabelle nicht als lückenlose Liste gelesen wird:

* *Von git erzeugte Zusammenführungen* (`Merge branch …`) fehlen. Sie tragen keine eigene
  Änderung, sondern nur die Naht zwischen zwei Branches
  (link:{adr}/0032-branches-nach-jedem-commit-mergen{adrext}[ADR 0032]).
* *Aufgehobene Commits* fehlen samt ihrem `Revert`. Das Werkzeug erkennt die Zeile
  `This reverts commit …` und lässt beide Seiten weg. Die Tabelle zeigt damit, was *geblieben*
  ist – nicht jeden Schritt, der einmal getan wurde. Vollständig ist allein `git log`.
* *Aussagelose Betreffe* fehlen: `Refinement`, `Add commit hash` und `Manueller commit` – die drei
  Messages, mit denen aus der IDE heraus committet wurde
  (link:{adr}/0051-git-historie-ohne-aussagelose-betreffe{adrext}[ADR 0051]). Sie benennen nicht
  eine Änderung, sondern den Umstand des Committens; ein Drittel der Zeilen bestand daraus. Wer
  auch sie sehen will, liest `git log`.

WARNING: Ein ausgelassener Commit hat *keinen* Anker `+commit-<kurzhash>+`. Nennt ein Log-Eintrag
ihn in seiner Zeile `+_Commit:_+`, zeigt der Verweis ins Leere und der Build wird rot. Der Task
warnt vorher und nennt Hash und Eintrag; die Ursache ist dann die Commit-Message, nicht das
Protokoll.
