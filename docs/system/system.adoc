Diese Dokumentation beschreibt das System *recipes* im Zusammenhang: welche Bausteine es
gibt, wie sie ineinandergreifen, welche Daten sie halten und wie das Ganze gebaut,
betrieben und geprüft wird.

== Zweck und Abgrenzung

Das Projekt kennt fünf Dokumentationsarten mit klar getrennten Aufgaben. Wer etwas ergänzt,
wählt danach den Ort:

[cols="1,2,3", options="header"]
|===
| Ort | Frage, die es beantwortet | Charakter

| `README.md`
| Wie fange ich an? Welcher Befehl tut was?
| Einstieg und Bedienung, bewusst knapp

| `docs/adr/`
| Warum ist es so und nicht anders?
| Eine Entscheidung je Datei, mit Optionen und Konsequenzen; historisch, wird nicht
  umgeschrieben

| `docs/system/` (hier)
| Was gibt es, und wie greift es ineinander?
| Zusammenhängende Sicht auf das System im *Ist-Zustand*

| `docs/backlog.adoc`
| Was kommt als Nächstes?
| Ein Prompt je Überschrift, von oben abzuarbeiten; der Status steht im Anfang der Überschrift
  (link:{adr}/0028-backlog-als-anhang-mit-status-im-titel{adrext}[ADR 0028]). Eingebunden als
  letzter Anhang <<backlog>>

| `docs/prompt/`
| Wie wird an diesem Projekt gearbeitet?
| Master-Prompt und Skills – Anweisung statt Beschreibung
  (link:{adr}/0023-asciidoc-fuer-masterprompt-und-skills{adrext}[ADR 0023]). Aufbau, Ladeweg und
  der vollständige Wortlaut stehen in <<arbeitsgrundlage>>; die Dateien dort bleiben die
  Quelle, das Kapitel bindet sie ein
|===

Daraus folgen drei Regeln für diese Dokumentation:

* *Sie verlinkt statt zu kopieren.* Begründungen stehen im jeweiligen ADR, nicht hier.
  Hier steht, was gilt – dahinter der Verweis, warum.
* *Sie nennt keine Versionsnummern.* Die einzige Quelle dafür ist
  `gradle/libs.versions.toml` bzw. `modules/frontend/package.json`
  (link:{adr}/0018-versionskatalog-libs-versions-toml{adrext}[ADR 0018]). Eine Version an zwei
  Stellen ist eine Version, die an einer Stelle veraltet.
* *Bei Widerspruch gewinnt der Code.* Diese Dateien sind Beschreibung, nicht Spezifikation.
  Ein Widerspruch ist ein Fehler in der Dokumentation und wird dort behoben.

Nicht Gegenstand dieser Dokumentation sind Betriebsanleitungen für eine konkrete
Zielumgebung (es gibt noch keine) und die Fachlichkeit der enthaltenen Rezepte.

Eine Ausnahme von „Beschreibung statt Anweisung" ist <<arbeitsgrundlage>>: Das Kapitel bindet
Master-Prompt und Skills im Wortlaut ein, damit sie hier mitlesbar sind. Eingebunden, nicht
kopiert – geändert werden sie in `docs/prompt`.

== Pflege dieser Dokumentation

Die Dokumentation wird *mit* der Änderung gepflegt, die sie betrifft – nicht nachgelagert.
Welche Änderung welches Kapitel berührt, steht in `docs/prompt/systemdoku.adoc`
(link:{adr}/0023-asciidoc-fuer-masterprompt-und-skills{adrext}[ADR 0023]); die
Entscheidung dazu in
link:{adr}/0022-asciidoc-systemdokumentation-in-docs-system{adrext}[ADR 0022].

Gerendert wird mit:

[source,bash]
----
./gradlew asciidoctor   # → build/docs/asciidoc/system.html
----

Neben dem HTML legt der Task die ADRs als `adr/` ab – gerendert von `./gradlew asciidoctorAdr`,
an dem er hängt (link:{adr}/0026-adrs-als-asciidoc{adrext}[ADR 0026]). Das Ergebnis ist damit
als Ganzes kopierbar und wird genau so ins Boot-Jar gepackt – die laufende Anwendung liefert es
unter `/recipes/docs/` aus
(link:{adr}/0024-systemdokumentation-im-boot-jar{adrext}[ADR 0024]).

Der Task läuft als Teil von `./gradlew build` mit. Ein fehlender `include`, eine
unbekannte Attribut-Referenz oder eine defekte Tabelle fällt damit im Build auf und nicht
erst beim Lesen. Seit dem Anhang <<quelldateien>> gilt das auch für die *Pfade der
Quelldateien*: Sie sind eingebunden, ein Umzug bricht den Build.
