= Überblick

== Aufgabe des Systems

*recipes* verwaltet Kochrezepte. Ein Rezept besteht aus Kopfdaten (Titel, Beschreibung,
Portionen, Zubereitungszeit, Schwierigkeitsgrad), einer Liste von Zutaten und einer
*geordneten* Folge von Zubereitungsschritten. Über die Oberfläche und über die REST-API
lassen sich Rezepte anlegen, lesen, ersetzen und löschen – mehr nicht. Es gibt keine
Nutzerverwaltung, keine Suche, keine Bewertungen, keine Bilder.

Fachlich vorbelegt ist die Datenbank mit dem klassischen Buchinger-Heilfastenzyklus
(siehe <<beispieldaten>> im Kapitel Datenmodell); das ist Beispieldatenbestand, keine
Fachlogik.

== Qualitätsziele

Die Reihenfolge ist bewusst: Bei einem Konflikt gewinnt das weiter oben stehende Ziel.

[cols="1,3,3", options="header"]
|===
| Ziel | Bedeutung | Woran es hängt

| Strukturtreue
| Die Abhängigkeitsrichtung der Schichten gilt ohne Ausnahme, auch unter Zeitdruck.
| Ein Gradle-Modul je Schicht, zusätzlich zwei ArchUnit-Sichten
  (Skill `docs/prompt/architektur.adoc`)

| Prüfbarkeit
| Jede Aussage über das System ist automatisiert nachweisbar – vom Datentyp bis zum
  Nutzer-Flow im echten Browser.
| Fünf Teststufen, siehe Kapitel Qualitätssicherung

| Typsicherheit an den Rändern
| Fehler fallen beim Kompilieren auf, nicht zur Laufzeit: SQL, API-Contract und
  Record-Konstruktion sind typisiert.
| jOOQ-Codegen aus dem Changelog, generierte TS-Typen aus OpenAPI, curried Factories
  (Skill `docs/prompt/architektur.adoc`)

| Einfachheit des Deployments
| Ein Artefakt, eine Origin, keine CORS-Konfiguration.
| Das Frontend wird ins Boot-Jar gepackt
  (Skill `docs/prompt/frontend.adoc`)

| Reproduzierbarer Build
| Derselbe Befehl führt auf jeder Maschine zum selben Ergebnis, ohne Docker und ohne
  lokale Datenbank.
| Gradle-Wrapper (Skill `docs/prompt/build.adoc`),
  Versionskatalog (Skill `docs/prompt/build.adoc`),
  embedded PostgreSQL (Skill `docs/prompt/tests.adoc`)
|===

.Das System und seine Nachbarn
[plantuml,systemkontext,svg]
....

nutzer --> browser : Rezepte pflegen

recipes --> db : JDBC (jOOQ)\nSchema-Migration (Liquibase)

....

Weitere Nachbarn gibt es nicht: Das System ruft von sich aus kein Fremdsystem auf. Das
Diagramm entsteht beim Rendern aus seiner Quelle in dieser Datei
(Skill `docs/prompt/systemdokumentation.adoc`).

[cols="1,1,3", options="header"]
|===
| Nachbar | Richtung | Schnittstelle

| Browser / API-Client
| eingehend
| HTTP: SPA unter `/recipes/`, JSON-API unter `/recipes/api/recipes`, Contract unter
  `/recipes/v3/api-docs`. Ein Port, eine Origin
  (Skill `docs/prompt/api.adoc`).

| PostgreSQL
| ausgehend
| JDBC. Zugangsdaten ausschließlich über Umgebungsvariablen, siehe Kapitel Betrieb. Das
  Schema wird beim Start von Liquibase angelegt bzw. fortgeschrieben.
|===

== Technische Bausteine im Groben

[cols="1,2,3", options="header"]
|===
| Baustein | Ort | Rolle

| Backend
| `modules/backend/`
| Java, Spring Boot. Vier Gradle-Module – ein Modul je Schicht der Hexagonal-Architektur.

| Frontend
| `modules/frontend/`
| TypeScript, React, react-router, Vite. Eigenständiges npm-Projekt, das beim Gradle-Build
  gebaut und ins Boot-Jar gelegt wird.

| Datenbankschema
| `modules/backend/adapter/src/main/resources/db/changelog/`
| Liquibase-Changelogs. Dieselben Dateien speisen zur Laufzeit die Migration und beim Build
  die jOOQ-Codegenerierung.

| Dokumentation
| `docs/`
| Diese Systemdokumentation (`docs/system/`), die Arbeitsgrundlage (`docs/prompt/`), das
  Session-Protokoll (`docs/log/claudeLog.adoc`, Anhang <<session-protokoll>>) und das Backlog
  (`docs/backlog.adoc`, Anhang <<backlog>>) – alles AsciiDoc
  (Skill `docs/prompt/systemdokumentation.adoc`). Das Protokoll ist eingebunden und damit
  Teil des Builds; seine Kennzahlen stehen als erzeugte Tabelle `docs/log/kennzahlen.adoc` im
  Anhang <<kennzahlen>>
  (Skill `docs/prompt/manager.adoc`).

| Arbeitsgrundlage
| `docs/prompt/` und `CLAUDE.md`
| Master-Prompt und zehn Skills – die Anweisungen, unter denen entwickelt wird. Kein Baustein
  der Anwendung, aber Teil des Repositorys; siehe <<arbeitsgrundlage>>.
|===

Alle Bausteine liegen unter `modules/`
(Skill `docs/prompt/architektur.adoc`); das Wurzelprojekt trägt keinen
Quellcode und aggregiert nur. Die Quellen selbst stehen im Anhang <<quelldateien>>.

== Randbedingungen

* *Java 25* als Toolchain-Vorgabe in allen Backend-Modulen; moderne Sprachmittel (Records,
  Pattern Matching, Text Blocks) sind ausdrücklich erwünscht.
* *Kein Lombok.* Records und Konstruktor-Injektion ersetzen es
  (Skill `docs/prompt/architektur.adoc`).
* *Gradle ausschließlich über den Wrapper*, Buildskripte im Kotlin-DSL
  (Skill `docs/prompt/build.adoc`).
* *Der Build braucht keine laufende Datenbank* – weder für die Codegenerierung noch für die
  Tests. Docker ist nicht erforderlich.
* *Code und JavaDoc auf Englisch*, Dokumentation und Oberfläche auf Deutsch.
* *Die Arbeitsweise ist versioniert.* Rolle, Grundregeln, Konventionen und die Definition of
  Done stehen als Master-Prompt und Skills im Repository, nicht im Gedächtnis der Beteiligten
  (`docs/prompt/prompt.adoc`).
