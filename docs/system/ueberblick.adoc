= Überblick

== Aufgabe des Systems

*recipes* verwaltet Kochrezepte. Ein Rezept besteht aus Kopfdaten (Titel, Beschreibung,
Portionen, Zubereitungszeit, Schwierigkeitsgrad), einer Liste von Zutaten und einer
*geordneten* Folge von Zubereitungsschritten. Über die Oberfläche und über die REST-API
lassen sich Rezepte anlegen, lesen, ersetzen und löschen – mehr nicht. Es gibt keine
Nutzerverwaltung, keine Suche, keine Bewertungen, keine Bilder.

Fachlich vorbelegt ist die Datenbank mit dem klassischen Buchinger-Heilfastenzyklus
(siehe <<beispieldaten>> im Kapitel Datenmodell); das ist Beispieldatenbestand, keine
Fachlogik.

== Systemkontext

Das System hat genau zwei Nachbarn: den Browser des Nutzers und eine PostgreSQL-Datenbank.
Es ruft von sich aus kein Fremdsystem auf.

----
        ┌────────────────┐
        │    Browser     │   Nutzer: Rezepte pflegen
        └───────┬────────┘
                │ HTTPS/HTTP  (SPA-Auslieferung + JSON über /recipes/api)
                ▼
        ┌────────────────────────────────────────────┐
        │  recipes  (ein Boot-Jar)                   │
        │  · SPA-Bundle aus dem Klassenpfad          │
        │  · REST-API                                │
        │  · OpenAPI-Dokument + Swagger UI           │
        └───────┬────────────────────────────────────┘
                │ JDBC (jOOQ), Schema-Migration (Liquibase)
                ▼
        ┌────────────────┐
        │   PostgreSQL   │
        └────────────────┘
----

[cols="1,1,3", options="header"]
|===
| Nachbar | Richtung | Schnittstelle

| Browser / API-Client
| eingehend
| HTTP: SPA unter `/recipes/`, JSON-API unter `/recipes/api/recipes`, Contract unter
  `/recipes/v3/api-docs`. Ein Port, eine Origin
  (link:{adr}/0016-context-path-recipes.md[ADR 0016]).

| PostgreSQL
| ausgehend
| JDBC. Zugangsdaten ausschließlich über Umgebungsvariablen, siehe Kapitel Betrieb. Das
  Schema wird beim Start von Liquibase angelegt bzw. fortgeschrieben.
|===

== Technische Bausteine im Groben

[cols="1,2,3", options="header"]
|===
| Baustein | Ort | Rolle

| Backend
| `modules/backend/`
| Java, Spring Boot. Vier Gradle-Module – ein Modul je Schicht der Hexagonal-Architektur.

| Frontend
| `modules/frontend/`
| TypeScript, React, react-router, Vite. Eigenständiges npm-Projekt, das beim Gradle-Build
  gebaut und ins Boot-Jar gelegt wird.

| Datenbankschema
| `modules/backend/adapter/src/main/resources/db/changelog/`
| Liquibase-Changelogs. Dieselben Dateien speisen zur Laufzeit die Migration und beim Build
  die jOOQ-Codegenerierung.

| Dokumentation
| `docs/`
| ADRs (`docs/adr/`), diese Systemdokumentation (`docs/system/`), Session-Protokoll
  (`docs/log/`).

| Arbeitsgrundlage
| `docs/prompt/` und `CLAUDE.md`
| Master-Prompt und fünf Skills – die Anweisungen, unter denen entwickelt wird. Kein Baustein
  der Anwendung, aber Teil des Repositorys; siehe <<arbeitsgrundlage>>.
|===

Alle Bausteine liegen unter `modules/`
(link:{adr}/0015-alle-bausteine-unter-modules.md[ADR 0015]); das Wurzelprojekt trägt keinen
Quellcode und aggregiert nur. Die Quellen selbst stehen im Anhang <<quelldateien>>.

== Randbedingungen

* *Java 25* als Toolchain-Vorgabe in allen Backend-Modulen; moderne Sprachmittel (Records,
  Pattern Matching, Text Blocks) sind ausdrücklich erwünscht.
* *Kein Lombok.* Records und Konstruktor-Injektion ersetzen es
  (link:{adr}/0003-kein-lombok-records-und-konstruktor-injektion.md[ADR 0003]).
* *Gradle ausschließlich über den Wrapper*, Buildskripte im Kotlin-DSL
  (link:{adr}/0009-gradle-wrapper-verbindlich.md[ADR 0009],
  link:{adr}/0010-gradle-kotlin-dsl.md[ADR 0010]).
* *Der Build braucht keine laufende Datenbank* – weder für die Codegenerierung noch für die
  Tests. Docker ist nicht erforderlich.
* *Code und JavaDoc auf Englisch*, Dokumentation und Oberfläche auf Deutsch.
* *Die Arbeitsweise ist versioniert.* Rolle, Grundregeln, Konventionen und die Definition of
  Done stehen als Master-Prompt und Skills im Repository, nicht im Gedächtnis der Beteiligten
  (link:{adr}/0023-asciidoc-fuer-masterprompt-und-skills.md[ADR 0023]).
