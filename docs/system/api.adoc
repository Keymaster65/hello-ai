= Schnittstellen

== Adressraum

Alles liegt unter dem Context-Path `/recipes`
(link:{adr}/0016-context-path-recipes{adrext}[ADR 0016]) – SPA, API und Contract teilen eine
Origin. Genau das macht CORS überflüssig
(link:{adr}/0007-react-frontend-mit-backend-als-bff{adrext}[ADR 0007]).

[cols="2,2,3", options="header"]
|===
| Zweck | Pfad | Anmerkung

| Oberfläche (SPA) | `/recipes/` | Bundle aus dem Klassenpfad (`static/`)
| REST-API | `/recipes/api/recipes` | JSON
| REST-API auf dem git-Store | `/recipes/api/gitdata/recipes` | dieselben Operationen auf der
  zweiten Ablage; *nur vorhanden*, wenn `recipes.gitdata.enabled` gesetzt ist
  (link:{adr}/0054-zweite-rest-front-auf-dem-gitdata-store{adrext}[ADR 0054])
| MCP-Server | `/recipes/api/mcp` | JSON-RPC 2.0, zustandslos, nur `POST`, nur lesend
  (link:{adr}/0049-mcp-service-fuer-rezepte-und-dokumentation{adrext}[ADR 0049])
| MCP über REST | `/recipes/api/mcp/…` | dieselben Werkzeuge und Ressourcen als gewöhnliche
  Operationen, im OpenAPI-Contract
  (link:{adr}/0050-rest-facade-des-mcp-service-in-openapi{adrext}[ADR 0050])
| OpenAPI 3.1, JSON | `/recipes/v3/api-docs` | zur Laufzeit erzeugt
| OpenAPI 3.1, YAML | `/recipes/v3/api-docs.yaml` | dasselbe Dokument
| Swagger UI | `/recipes/swagger-ui.html` | Operationen nach Methode, Tags alphabetisch
| Systemdokumentation | `/recipes/docs/` | dieses Dokument, gerendert und im Jar
  (link:{adr}/0024-systemdokumentation-im-boot-jar{adrext}[ADR 0024])
| ADRs | `/recipes/docs/adr/\{datei}.html` | gerendertes AsciiDoc, aus der Doku heraus
  verlinkt (link:{adr}/0026-adrs-als-asciidoc{adrext}[ADR 0026])
| Meldeweg | `/.well-known/security.txt` | *ohne* Context-Path – RFC 9116 kennt nur den
  Ursprung (link:{adr}/0037-security-txt-am-ursprung-per-engine-valve{adrext}[ADR 0037])
|===

Die letzte Zeile ist die einzige Ausnahme von „alles unter `/recipes`". Sie ist keine
Nachlässigkeit, sondern Vorschrift: RFC 9116 nennt genau einen Ort für den maschinenlesbaren
Meldeweg, und der liegt im Ursprung. Ausgeliefert wird die Datei deshalb nicht von Spring MVC –
dorthin gelangt eine Anfrage außerhalb des Context-Path gar nicht –, sondern von
<<src-security-txt-valve,`SecurityTxtValve`>> in der Tomcat-Pipeline; ihr Inhalt stammt aus
<<src-security-txt-properties,`SecurityTxtProperties`>> und damit aus der Konfiguration.

Die Adresse der Dokumentation endet auf einen Schrägstrich. `/recipes/docs` leitet dorthin
um, statt weiterzuleiten: Nur mit dem Schrägstrich lösen die relativen Verweise auf die ADRs
im Browser richtig auf. Beides richtet <<src-documentation-routing-config,`DocumentationRoutingConfig`>>
ein, weil Spring Boot eine Verzeichnis-Startseite nur für die Wurzel der Anwendung kennt.

== REST-Ressource `recipes`

[cols="1,3,1,4", options="header"]
|===
| Methode | Pfad | Erfolg | Fehler

| `POST` | `/api/recipes` | `201` + `Location` | `400`
| `GET` | `/api/recipes` | `200` (ggf. leere Liste) | –
| `GET` | `/api/recipes/\{id}` | `200` | `404`
| `PUT` | `/api/recipes/\{id}` | `200` | `400`, `404`
| `DELETE` | `/api/recipes/\{id}` | `204` (ohne Body) | `404`
|===

`PUT` *ersetzt* das Rezept vollständig, einschließlich Zutaten und Schritte; es gibt keine
teilweise Änderung (kein `PATCH`). Ein im Request mitgeschickter Identifikator wird
ignoriert – maßgeblich ist der Pfad.

[[recipes-auf-dem-gitdata-store]]
=== Dieselben Operationen auf dem git-Store

Unter `+/api/gitdata/recipes+` stehen *dieselben fünf Operationen* mit denselben Anfragen,
Antworten und Fehlerbildern – bedient aber von der zweiten Ablage, die jede Zeile als JSON-Datei in
einen git-Branch schreibt (link:{adr}/0053-gitdata-adapter-rezepte-als-json-im-branch-data{adrext}[ADR
0053], link:{adr}/0054-zweite-rest-front-auf-dem-gitdata-store{adrext}[ADR 0054]). Beschrieben ist
das hier deshalb nicht zweimal; es gilt Wort für Wort, was oben steht, mit drei Unterschieden:

* *Die Adresse muss eingeschaltet sein.* Ohne `recipes.gitdata.enabled=true` gibt es sie nicht –
  keine leere Antwort, sondern `404` wie für jeden unbekannten Pfad. Die Konfiguration steht im
  Kapitel Build und Betrieb.
* *Die beiden Ablagen sind getrennt.* Ein Rezept, das hier entsteht, ist unter `/api/recipes` nicht
  zu sehen und umgekehrt; auch die Identifikatoren werden unabhängig vergeben. Es gibt keine
  Synchronisation zwischen ihnen.
* *Der `Location`-Header zeigt auf diese Front*, also auf `+/api/gitdata/recipes/{id}+`.

Im OpenAPI-Contract erscheinen beide Fronten – die zweite unter dem Tag „Recipes (gitdata)", und
auch sie nur, wenn sie eingeschaltet ist.

=== Anfrage

<<src-recipe-request,`RecipeRequest`>>, validiert per Bean Validation. Verstöße erzeugen `400` mit einem Eintrag
je Feld.

[cols="2,1,3", options="header"]
|===
| Feld | Pflicht | Regel

| `title` | ja | nicht leer, maximal 200 Zeichen
| `description` | nein | Freitext, unbegrenzt
| `servings` | nein | wenn vorhanden, echt positiv
| `prepTimeMinutes` | nein | wenn vorhanden, echt positiv
| `difficulty` | ja | `EASY`, `MEDIUM` oder `HARD`
| `ingredients[]` | nein | je Element geprüft: `name` nicht leer und ≤ 200 Zeichen, `quantity` ≥ 0, `unit` ≤ 50 Zeichen
| `steps[]` | nein | je Element geprüft: `instruction` nicht leer
|===

Die Reihenfolge der Listen ist bedeutungstragend: Aus ihr entstehen die Positionen. Ein
`null` oder fehlendes Feld für `ingredients`/`steps` wird als leere Liste behandelt.

.Beispiel
[source,json]
----
{
  "title": "Spaghetti Carbonara",
  "description": "Klassische römische Pasta",
  "servings": 4,
  "prepTimeMinutes": 25,
  "difficulty": "MEDIUM",
  "ingredients": [
    { "name": "Spaghetti", "quantity": 500, "unit": "g" },
    { "name": "Eier", "quantity": 4, "unit": "Stk" }
  ],
  "steps": [
    { "instruction": "Nudeln kochen" },
    { "instruction": "Eier und Käse verrühren" }
  ]
}
----

=== Antwort

<<src-recipe-response,`RecipeResponse`>> entspricht dem Request, ergänzt um `id`; die Schritte tragen zusätzlich
ihre `position`. Die vom Domänenmodell garantierten Felder sind im Contract als
`required` markiert (`id`, `title`, `difficulty`, `ingredients`, `steps`), die echt
optionalen nicht (`description`, `servings`, `prepTimeMinutes`).

Das ist mehr als Kosmetik: Der TypeScript-Generator übernimmt die Unterscheidung, sodass im
Frontend `id: number` statt `id?: number` steht und garantierte Felder ohne Prüfung auf
`undefined` benutzbar sind.

=== Fehler

Jeder Fehler antwortet als *Problem Detail* nach
https://www.rfc-editor.org/rfc/rfc9457.html[RFC 9457], im Medientyp
`+application/problem+json+` (link:{adr}/0046-rfc-9457-problem-details-als-fehlerformat{adrext}[ADR
0046]). Der Rumpf ist <<src-problem-detail,`ProblemDetail`>>, zentral erzeugt im
<<src-global-exception-handler,`GlobalExceptionHandler`>>:

[source,json]
----
{
  "type": "/recipes/docs/#problem-validation-failed",
  "title": "Request validation failed",
  "status": 400,
  "detail": "1 field(s) of the request body are invalid",
  "instance": "/recipes/api/recipes",
  "fieldErrors": [
    { "field": "title", "message": "must not be blank" }
  ]
}
----

[cols="1,3", options="header"]
|===
| Feld | Bedeutung

| `type`
| Kennzeichnet die *Art* des Problems und zeigt zugleich auf den Abschnitt dieser
  Dokumentation, der sie beschreibt – die Anker unten. Der Präfix ist der Context-Path der
  Anfrage, nicht ein fest verdrahteter Wert.

| `title`
| Kurzfassung der Problemart, über alle Vorkommen gleich.

| `status`
| Der HTTP-Statuscode, derselbe wie in der Statuszeile.

| `detail`
| Erklärung *dieses* Vorkommens. Nie `null`: Bringt eine Ausnahme keine Meldung mit, steht hier
  der `title`.

| `instance`
| Die Anfrage, die das Problem ausgelöst hat, inklusive Context-Path.

| `fieldErrors`
| Erweiterung über RFC 9457 hinaus: ein Eintrag je verletztem Feld. Außerhalb der Validierung
  eine *leere* Liste, nicht `null`. Das Frontend verlässt sich darauf
  (`ApiError.fieldError(feld)`).
|===

==== Die Problemarten

Die vier Arten stehen in <<src-problem-type,`ProblemType`>>; jede kennt ihren Titel und ihren
Statuscode. Die Anker sind das Ziel der `type`-URI – wer sie im Browser öffnet, landet hier.

[[problem-not-found]]
`not-found` (`404`, „Recipe not found"):: Ausgelöst von `RecipeNotFoundException` – zu dem
Bezeichner im Pfad gibt es kein Rezept. `detail` nennt den Bezeichner, `fieldErrors` ist leer.

[[problem-validation-failed]]
`validation-failed` (`400`, „Request validation failed"):: Ein Verstoß gegen die Bean
Validation des Request-DTO (`MethodArgumentNotValidException`). Als einzige Art füllt sie
`fieldErrors`, mit einem Eintrag je verletztem Feld; verschachtelte Felder stehen mit Index
(`+ingredients[1].name+`).

[[problem-malformed-request]]
`malformed-request` (`400`, „Malformed request body"):: Der Rumpf ließ sich nicht als JSON
lesen (`HttpMessageNotReadableException`). `detail` ist bewusst ein fester Satz und *nicht* die
Meldung der Ausnahme: Die zitierte den fehlerhaften Rumpf und nannte Klassen von Jackson.

[[problem-invalid-argument]]
`invalid-argument` (`400`, „Invalid argument"):: Eine `IllegalArgumentException` – in aller
Regel eine verletzte Invariante eines Domänen-Records. `detail` ist deren Meldung.

Der letzte Fall verdient Aufmerksamkeit: Die Domänen-Records werfen
`IllegalArgumentException`/`NullPointerException` bei verletzten Invarianten. Nur die
`IllegalArgumentException` wird zu `400`; ein `NullPointerException` aus dem Konstruktor
würde als `500` durchschlagen. In der Praxis fängt die Bean Validation diese Fälle vorher
ab – die Reihenfolge ist also Absicherung, keine Redundanz ohne Zweck.

==== Fehler des Frameworks

`+spring.mvc.problemdetails.enabled+` steht auf `true`. Damit antworten auch die Fälle, für die
es keinen eigenen Handler gibt – `405` bei falscher Methode, `415` bei falschem Medientyp –
als `+application/problem+json+`, mit Springs eigenem Rumpf. Er trägt dieselben fünf Felder des
RFC, aber *kein* `fieldErrors`; das Frontend behandelt es deshalb als optional.

== OpenAPI-Contract

Der Contract wird zur *Laufzeit* aus Controller-Signaturen, Bean-Validation und den
`@Operation`/`@Schema`-Annotationen erzeugt
(link:{adr}/0005-springdoc-openapi-und-swagger-ui{adrext}[ADR 0005]). Es gibt keine
handgepflegte Spezifikationsdatei, die veralten könnte.

Dokumentweite Angaben (Titel, Beschreibung, Version, Kontakt, Lizenz) stehen in
<<src-openapi-config,`OpenApiConfig`>> im Modul `:bootstrap`; alles Operations- und Schemaspezifische steht als
Annotation an dem Adapter, der die Operation anbietet – am REST-Adapter für die Rezepte, am
MCP-Adapter für die Fassade aus <<mcp-ueber-rest>>
(link:{adr}/0050-rest-facade-des-mcp-service-in-openapi{adrext}[ADR 0050]).

`OpenApiDocumentationTest` prüft, dass das Dokument alle Operationen und Schemata
beschreibt und die Swagger UI ausgeliefert wird – der Contract ist damit nicht nur
vorhanden, sondern geprüft.

=== Abgeleitete TypeScript-Typen

Das Frontend nutzt keine handgeschriebenen API-Typen. `src/api/schema.d.ts` wird aus dem
Contract generiert und ist eingecheckt:

[source,bash]
----
cd modules/frontend && npm run generate:api   # benötigt ein laufendes Backend auf :8080
----

[IMPORTANT]
====
Nach jeder API-Änderung ist dieser Schritt fällig. Er ist *nicht* Teil des Gradle-Builds,
weil er ein laufendes Backend braucht. Unterbleibt er, bleibt das Frontend gegen einen
veralteten Contract typisiert – der Build ist grün und die Laufzeit falsch.
====

== MCP-Schnittstelle

Unter `+/recipes/api/mcp+` antwortet ein Server des *Model Context Protocol* – dieselben Daten
wie die REST-API, aber in der Form, in der ein Sprachmodell sie ohne Vorwissen findet
(link:{adr}/0049-mcp-service-fuer-rezepte-und-dokumentation{adrext}[ADR 0049]). Die Bausteine
dahinter stehen im Kapitel Bausteine und Schichten, Abschnitt „Eingehender Adapter: MCP".

Der Server hat *zwei Fronten* auf einen Bestand: den Protokollendpunkt und – unterhalb desselben
Pfades – eine REST-Fassade, die im OpenAPI-Contract steht
(link:{adr}/0050-rest-facade-des-mcp-service-in-openapi{adrext}[ADR 0050], siehe
<<mcp-ueber-rest>>). Werkzeuge, Ressourcen und Fehlerbilder unten gelten für beide; was sich
unterscheidet, steht dort.

=== Transport

[cols="1,3", options="header"]
|===
| Regel | Verhalten

| Methode
| Nur `POST`. Ein `GET` antwortet `405`: Ohne Sitzung gibt es keinen Datenstrom, den der Server
  offen hielte.

| `Accept`
| Muss *beide* Medientypen nennen – `application/json` und `text/event-stream`. Fehlt einer,
  antwortet der Transport `400`. So schreibt es Streamable HTTP vor.

| `Origin`
| Eine Anfrage *mit* diesem Header wird mit `403` abgewiesen. Erlaubt ist keine Origin: Der
  Endpunkt ist für Werkzeuge gedacht, nicht für Seiten im Browser – das ist der Schutz gegen
  DNS-Rebinding.

| Sitzung
| Keine. Jede Anfrage ist für sich vollständig; `initialize` ist eine Auskunft, keine Anmeldung.
|===

=== Werkzeuge

Alle vier sind als lesend gekennzeichnet (`+readOnlyHint+`) und beschreiben ihre Eingabe über ein
JSON-Schema, das der Server *vor* dem Aufruf prüft.

[cols="1,1,3", options="header"]
|===
| Name | Eingabe | Ergebnis

| `+list_recipes+`
| –
| JSON-Array aller Rezepte mit `id`, `title`, `description`, `servings`, `prepTimeMinutes` und
  `difficulty` – ohne Zutaten und Schritte

| `+get_recipe+`
| `id` (ganze Zahl ≥ 1)
| Ein Rezept als JSON, zusätzlich mit `ingredients` und den `steps` samt `position`

| `+list_documentation+`
| –
| JSON-Array der Seiten der Systemdokumentation mit `id`, `title` und `uri`

| `+read_documentation+`
| `id` (nicht leerer Text)
| Die Seite als HTML – die Form, in der sie ausgeliefert wird
  (link:{adr}/0024-systemdokumentation-im-boot-jar{adrext}[ADR 0024])
|===

Die Namen sind Teil der Schnittstelle: Eine Umbenennung ist für jeden Client sichtbar.

=== Ressourcen

Jede Seite der Dokumentation ist zusätzlich eine Ressource – `+recipes://docs/system+` für das
Kapitelwerk, `+recipes://docs/adr/<datei ohne endung>+` je Architekturentscheidung, jeweils mit
dem Medientyp `text/html`. Der Katalog entsteht beim Start der Anwendung; ein mit
`+-PskipDocs+` gebautes Deployable hat ihn leer.

Rezepte sind *keine* Ressourcen: Der Katalog eines zustandslosen Servers ist nach dem Start
fest, ein neu angelegtes Rezept fehlte darin.

=== Fehlerbilder

Ein *fachlicher* Fehler ist ein Ergebnis, kein Protokollfehler: Das Werkzeug antwortet mit
`+isError+` und einem Satz, der die angefragte Kennung nennt – dieselbe Sparsamkeit wie bei den
Problem Details der REST-API (link:{adr}/0046-rfc-9457-problem-details-als-fehlerformat{adrext}[ADR
0046]), ohne Stacktrace, SQL oder Klassennamen. Ein *Protokoll*fehler – unbekannte Methode,
unbekanntes Werkzeug, Eingabe gegen das Schema – kommt als JSON-RPC-`error` zurück.

.Aufruf von Hand
[source,bash]
----
curl -X POST http://localhost:8080/recipes/api/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
----

[[mcp-ueber-rest]]
=== Dieselben Werkzeuge über REST

Unterhalb des Protokollendpunkts liegt eine *REST-Fassade*: eine Operation je Methode des
Protokolls, beschrieben im OpenAPI-Contract und damit in der Swagger UI bedienbar
(link:{adr}/0050-rest-facade-des-mcp-service-in-openapi{adrext}[ADR 0050]). Sie zeigt den
*Zugang*, nicht den Bestand – ein neues Werkzeug erscheint in ihr, ohne dass sie wächst.

[cols="2,1,3", options="header"]
|===
| Methode und Pfad | Entspricht | Erfolg / Fehler

| `GET /api/mcp/server`
| `initialize`
| `200`: Name, Version und die Anleitung, die ein Protokollclient bekommt

| `GET /api/mcp/tools`
| `tools/list`
| `200`: alle Werkzeuge mit `name`, `title`, `description` und `inputSchema`

| `POST /api/mcp/tools/\{name}`
| `tools/call`
| `200`: das Werkzeugergebnis mit `content` und `isError` · `404`: kein Werkzeug dieses Namens

| `GET /api/mcp/resources`
| `resources/list`
| `200`: alle Ressourcen mit `uri`, `name`, `title`, `description` und `mimeType`

| `GET /api/mcp/resources/content?uri=…`
| `resources/read`
| `200`: die Inhaltsblöcke mit `uri`, `mimeType` und `text` · `404`: keine Ressource dieser URI
|===

Der *Rumpf einer Werkzeuganfrage sind die Argumente* – das JSON-Objekt, das das `inputSchema` des
Werkzeugs beschreibt. Ein Werkzeug ohne Argumente braucht keinen Rumpf. Geprüft wird gegen dasselbe
Schema wie am Protokollendpunkt, *vor* dem Aufruf.

Die Antworten sind DTOs dieses Projekts, keine Typen des MCP-SDK:
<<src-mcp-server-info-dto,`McpServerInfoDto`>>, <<src-mcp-tool-dto,`McpToolDto`>>,
<<src-mcp-tool-result-dto,`McpToolResultDto`>>, <<src-mcp-resource-dto,`McpResourceDto`>> und
<<src-mcp-resource-content-dto,`McpResourceContentDto`>>. Sie lassen weg, was nur das Protokoll
braucht, und halten den veröffentlichten Contract von der Versionsfolge des SDK fern.

Drei Punkte unterscheiden die Fassade vom Protokollendpunkt:

* *Der Statuscode trennt anders.* Ein Name, den niemand trägt, ist `404` als Problem Detail nach
  https://www.rfc-editor.org/rfc/rfc9457.html[RFC 9457] – mit dem Rumpf des Rahmenwerks, nicht dem
  des <<src-global-exception-handler,`GlobalExceptionHandler`>> (siehe „Fehler des Frameworks").
  Ein *gelaufenes* Werkzeug, das einen Fehlschlag meldet, antwortet `200` mit `+isError+`: Das
  Ergebnis ist die Antwort, wie im Protokoll.
* *Kein `Accept` mit zwei Medientypen, keine Sitzungsregeln.* Es ist gewöhnliches HTTP.
* *Keine Origin-Prüfung.* Eine Anfrage mit `Origin`-Header wird hier *nicht* abgewiesen; sie läuft
  durch Spring MVC und damit am Ventil des Transports vorbei. Neue Daten gibt das nicht frei –
  Rezepte und Dokumentation liegen ohnehin offen –, es steht aber als Zeile im Kapitel Betrieb,
  Abschnitt <<offene-punkte>>.

.Aufruf von Hand
[source,bash]
----
curl http://localhost:8080/recipes/api/mcp/tools
curl -X POST http://localhost:8080/recipes/api/mcp/tools/get_recipe \
  -H 'Content-Type: application/json' -d '{"id":1}'
----

== Oberfläche

[cols="1,2,3", options="header"]
|===
| Ansicht | Adresse | Bemerkung

| Liste | `/recipes/` | Startseite
| Anlegen | `/recipes/new` | Formular, Modus `create`
| Detail | `/recipes/\{id}` | teilbarer Link
| Bearbeiten | `/recipes/\{id}/edit` | Formular, Modus `edit`

Damit diese Adressen auch beim *direkten* Aufruf funktionieren, leitet
<<src-spa-forwarding-controller,`SpaForwardingController`>> sie serverseitig auf die `index.html` weiter – explizit
aufgezählt, damit der Fallback API, OpenAPI und Swagger UI nicht verschattet
(link:{adr}/0017-router-mit-spa-fallback{adrext}[ADR 0017]). Die Detail- und Bearbeiten-Routen
sind serverseitig auf Ziffern eingeschränkt (`{id:\\d+}`).

== Keine weiteren Schnittstellen

Das System bietet *keine* Authentifizierung, keine Autorisierung, kein Rate Limiting, keine
Ereignis- oder Messaging-Schnittstelle und keine Actuator-Endpunkte. Wer die Anwendung
erreicht, darf alles – auch der MCP-Endpunkt und seine REST-Fassade sind offen, dort allerdings nur
lesend. Siehe Kapitel Betrieb, Abschnitt <<offene-punkte>>.
