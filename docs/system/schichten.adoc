= Bausteine und Schichten

== Die Regel

Das Backend folgt einer Hexagonal-/Clean-Architecture mit *einem Gradle-Modul je Schicht*
(Skill `docs/prompt/architektur.adoc`). Abhängigkeiten zeigen nach innen:

.Abhängigkeiten der Gradle-Module, wie sie in den Buildskripten deklariert sind
[plantuml,modulabhaengigkeiten,svg]
....
@startuml
!pragma layout smetana
skinparam shadowing false
skinparam componentStyle rectangle
skinparam defaultTextAlignment center

package "modules/backend" as backend {
  [bootstrap]
  [adapter]
  [application]
  [domain]
}

[frontend]

[bootstrap] --> [adapter] : implementation
[adapter] --> [application] : api
[application] --> [domain] : api
[bootstrap] ..> [frontend] : npm-Build ins Boot-Jar
@enduml
....

`api` bedeutet, dass die Abhängigkeit *durchgereicht* wird – ein Port zeigt Domänentypen, also
braucht sie auch, wer den Port benutzt. `implementation` behält sie für sich:
`:modules:backend:bootstrap` deklariert nur den Adapter, Anwendung und Domäne kommen
transitiv. `modules/frontend` ist kein Gradle-Modul, sondern ein npm-Projekt; sein Build wird
von `:modules:backend:bootstrap` ins Boot-Jar gepackt
(Skill `docs/prompt/architektur.adoc`). Das Diagramm entsteht beim
Rendern aus seiner Quelle in dieser Datei
(Skill `docs/prompt/systemdokumentation.adoc`).

Entscheidend ist, dass die Regel nicht nur dokumentiert, sondern *dreifach* abgesichert ist:

. *Vom Build erzwungen.* Ein Modul sieht nur, was es deklariert. Ein Import aus einer
  äußeren Schicht compiliert nicht. `:domain` und `:application` haben dabei überhaupt keine
  Framework-Abhängigkeit – Framework-Freiheit ist in beiden inneren Schichten strukturell
  garantiert, nicht bloß geprüft
  (Skill `docs/prompt/architektur.adoc`).
. *Von ArchUnit als Schichtenstapel geprüft* (<<src-layered-architecture-test,`LayeredArchitectureTest`>>): zusätzlich
  Framework-Freiheit von Domäne und Anwendungsschicht, die Teilung in `model`/`services` und
  „Ports sind Interfaces" (Skill `docs/prompt/architektur.adoc`).
. *Von ArchUnit als Zwiebelschalen geprüft* (<<src-onion-architecture-test,`OnionArchitectureTest`>>): Adapter kennen
  einander nicht – der REST-Adapter greift nicht am Port vorbei auf die Persistenz zu. Diese
  Lücke kann die Schichtensicht nicht schließen, weil beide Adapter im selben Modul liegen
  (Skill `docs/prompt/architektur.adoc`).

Fehlt einer Klasse eine Abhängigkeit, ist das ein Hinweis auf einen Schichtverstoß – nicht
die Aufforderung, sie im Buildskript zu ergänzen.

== Domäne

`Recipe` ist die Aggregatwurzel: ein Rezept *mit* seinen Zutaten und Schritten. Alle
Domänentypen sind unveränderliche Records.

[cols="1,3", options="header"]
|===
| Zusicherung | Wo sie steht

| `title` ist nicht `null` und nicht leer, `difficulty` ist nicht `null`
| kanonischer Konstruktor von `Recipe`

| `ingredients` und `steps` sind niemals `null`
| kanonischer Konstruktor: `null` wird zur leeren Liste, sonst `List.copyOf`; damit ist die
  Liste auch gegen Änderung von außen geschützt

| `id == null` bedeutet „noch nicht persistiert"
| Konvention des Modells; `withId(…)` liefert eine Kopie mit Identifikator

| Reihenfolge der Schritte
| `PreparationStep.position()`, 1-basiert
|===

Die vier Records samt Paketmarkierung stehen im Original in <<src-gruppe-domaene>>.

Records mit mehr als zwei Komponenten bieten zusätzlich eine curried Factory `curried()` –
eine Kette benannter Einzelschritte, die Reihenfolge und Vollständigkeit über das Typsystem
erzwingt (Skill `docs/prompt/architektur.adoc`).
Der kanonische Konstruktor bleibt der einzige Ort der Validierung.

== Anwendungsschicht

`RecipeServiceImpl` implementiert den eingehenden Port – als *gewöhnliche Java-Klasse*, ohne
eine einzige Annotation. Die Schicht kennt weder Web noch Persistenztechnik noch Spring: Im
Buildskript steht außer `:domain` keine Produktionsabhängigkeit
(Skill `docs/prompt/architektur.adoc`).

Beides, was dafür nötig ist, liegt im Composition Root `:bootstrap`:
`ApplicationServicesConfig` erzeugt die Bean, `TransactionalRecipeService` umschließt jeden
Use Case mit einer Transaktion – lesende read-only, schreibende schreibend. Die
*Transaktionsgrenze ist damit weiterhin der Use Case*, nur ihre Formulierung steht außerhalb
der Schicht.

Die Übersetzung „nicht gefunden" → Fehlerbild geschieht hier durch
`RecipeNotFoundException`; welchen HTTP-Status daraus wird, entscheidet erst der Adapter.
Das ist die Stelle, an der die Richtung der Abhängigkeit sichtbar wird: Die Anwendung kennt
keinen Statuscode.

[cols="1,3", options="header"]
|===
| Use Case | Verhalten

| `create(Recipe)` | Speichert; ein mitgegebener Identifikator wird ignoriert.
| `getById(long)` | Liefert das Rezept oder wirft `RecipeNotFoundException`.
| `getAll()` | Liefert alle Rezepte, ggf. eine leere Liste.
| `update(long, Recipe)` | Ersetzt vollständig; wirft `RecipeNotFoundException`, wenn es das Rezept nicht gibt.
| `delete(long)` | Löscht; wirft `RecipeNotFoundException`, wenn nichts gelöscht wurde.
|===

== Eingehender Adapter: REST

`RecipeController` bleibt dünn – er mappt, delegiert an den Port und setzt den Statuscode;
Geschäftslogik enthält er nicht. Die OpenAPI-Annotationen sitzen direkt an dieser Schicht,
damit der Contract neben dem Code steht, den er beschreibt
(Skill `docs/prompt/api.adoc`).

`RecipeRestMapper` trennt API und Domäne. Zwei Festlegungen stecken darin:

* Die *Position eines Zubereitungsschritts* wird aus der Reihenfolge der Liste im Request
  abgeleitet (1-basiert) – der Client schickt keine Positionen mit.
* `null`-Listen im Request werden zu leeren Listen, bevor die Domäne sie sieht.

`GlobalExceptionHandler` (`@RestControllerAdvice`) übersetzt Exceptions zentral in ein
Problem Detail nach RFC 9457
(Skill `docs/prompt/api.adoc`); die Zuordnung
steht im Kapitel API.

`SpaForwardingController` leitet die Routen der Oberfläche serverseitig auf die
`index.html` weiter, damit ein geteilter Link wie `/recipes/3` nicht im 404 endet. Die
Routen sind *einzeln aufgezählt* statt per Wildcard gefangen, weil ein Catch-all API,
OpenAPI-Dokument und Swagger UI verschatten könnte
(Skill `docs/prompt/api.adoc`).

[WARNING]
====
Eine neue Route im Frontend braucht eine zusätzliche Methode in
`SpaForwardingController`. Vergisst man sie, funktioniert die Route beim Navigieren
innerhalb der SPA, aber nicht beim direkten Aufruf. Der zugehörige Systemtest schlägt in
diesem Fall fehl.
====

== Ausgehender Adapter: Persistenz

`RecipeJooqRepository` implementiert den ausgehenden Port mit typsicherem SQL über jOOQ.
Der generierte Code entsteht beim Build aus dem Liquibase-Changelog, ohne laufende
Datenbank (siehe Kapitel Datenmodell).

Bemerkenswerte Eigenschaften der Implementierung:

[cols="1,3", options="header"]
|===
| Aspekt | Umsetzung

| Lesen einer Liste
| `findAll()` lädt Rezepte, Zutaten und Schritte in *drei* Abfragen und gruppiert im
  Speicher – kein N+1 über die Zahl der Rezepte.

| Sortierung
| Kinder werden immer `ORDER BY position` geladen, Rezepte `ORDER BY id`. Die Reihenfolge
  in der Antwort ist damit deterministisch.

| Ersetzen (`update`)
| Kopfdaten per `UPDATE` inklusive `updated_at`; Zutaten und Schritte werden *komplett
  gelöscht und neu eingefügt*. Das hält die Positionen konsistent mit der eingehenden
  Reihenfolge, vergibt aber neue technische Schlüssel für die Kinder.

| Löschen
| Nur das Rezept wird gelöscht; Zutaten und Schritte verschwinden über
  `ON DELETE CASCADE`. Der Rückgabewert `boolean` unterscheidet „gelöscht" von „gab es
  nicht" und trägt so die 404-Entscheidung in die Anwendungsschicht.

| Sichtbarkeit
| Repository und Mapper sind *paketprivat*. Von außen ist nur der Port sichtbar.
|===

== Laufzeitsicht

Zwei Abläufe genügen, um das Zusammenspiel zu zeigen; die übrigen Use Cases folgen
demselben Muster.

.Lesen: GET /recipes/api/recipes/\{id}
[plantuml,ablauf-lesen,svg]
....
@startuml
!pragma layout smetana
skinparam shadowing false

actor Browser
participant "RecipeController" as controller
participant "TransactionalRecipeService" as tx
participant "RecipeServiceImpl" as service
participant "RecipeJooqRepository" as repository
database "PostgreSQL" as db
participant "GlobalExceptionHandler" as handler

Browser -> controller : GET /recipes/api/recipes/1
controller -> tx : getById(id)
note right of tx : öffnet die readOnly-Transaktion
tx -> service : getById(id)
service -> repository : findById(id)
repository -> db : SELECT recipe, ingredient, preparation_step
db --> repository
repository --> service : Optional
alt Optional ist leer
  service --> tx : RecipeNotFoundException
  tx --> controller : RecipeNotFoundException
  controller -> handler : Exception
  handler --> Browser : 404 + ProblemDetail
else Rezept vorhanden
  service --> tx : Recipe
  tx --> controller : Recipe
  note left of controller : RecipeRestMapper.toResponse(...)
  controller --> Browser : 200 + RecipeResponse
end
@enduml
....

.Anlegen: POST /recipes/api/recipes
[plantuml,ablauf-anlegen,svg]
....
@startuml
!pragma layout smetana
skinparam shadowing false

actor Browser
participant "Bean Validation" as validation
participant "RecipeController" as controller
participant "RecipeRestMapper" as mapper
participant "TransactionalRecipeService" as tx
participant "RecipeServiceImpl" as service
participant "RecipeJooqRepository" as repository
participant "GlobalExceptionHandler" as handler

Browser -> validation : POST /recipes/api/recipes\n(RecipeRequest)
alt Request ungültig
  validation -> handler : MethodArgumentNotValidException
  handler --> Browser : 400 + ProblemDetail\n(fieldErrors je Feld)
else Request gültig
  validation -> controller : create(request)
  controller -> mapper : toDomain(request)
  note right of mapper : Positionen aus der Listenordnung;\nder Recipe-Konstruktor prüft\ndie Domäneninvarianten
  mapper --> controller : Recipe
  controller -> tx : create(recipe)
  note right of tx : öffnet die schreibende Transaktion
  tx -> service : create(recipe)
  service -> repository : save(recipe)
  repository -> repository : INSERT recipe,\ndann INSERT je Zutat und Schritt
  repository --> service : Recipe mit id
  service --> tx : Recipe mit id
  tx --> controller : Recipe mit id
  controller --> Browser : 201 + Location + RecipeResponse
end
@enduml
....

Die Quellen der beteiligten Klassen stehen in <<src-gruppe-rest>>, <<src-gruppe-application>>
und <<src-gruppe-persistence>>.

Der Start der Anwendung läuft in dieser Reihenfolge: Spring Boot hochfahren →
Liquibase-Migration gegen die konfigurierte Datenbank → `DSLContext` bereitstellen → HTTP
öffnen. Ist die Datenbank nicht erreichbar, startet die Anwendung nicht.

== Frontend

Das Frontend ist eine React-SPA mit `react-router`
(Skill `docs/prompt/frontend.adoc`) und spricht ausschließlich
*relative* Pfade an – abgeleitet aus `import.meta.env.BASE_URL`, das den Context-Path des
Backends spiegelt. Eine absolute Origin steht nirgends im Code, deshalb ist derselbe Build
in Entwicklung und Produktion gültig.

[cols="1,3", options="header"]
|===
| Baustein | Aufgabe

| <<src-app-tsx,`src/App.tsx`>>
| Routen: `/` (Liste), `/new` (Anlegen), `/:id` (Detail), `/:id/edit` (Bearbeiten), sonst
  eine Nicht-gefunden-Seite. `basename` kommt aus `BASE_URL`.

| `src/pages/`
| Seiten je Route: <<src-recipe-list-page,`RecipeListPage`>>,
  <<src-recipe-detail-page,`RecipeDetailPage`>>, <<src-recipe-form-page,`RecipeFormPage`>>
  (Modus `create`
  oder `edit`). Sie lesen die Route-Parameter, laden Daten und behandeln Lade- und
  Fehlerzustände.

| `src/components/`
| Darstellung: <<src-recipe-list,`RecipeList`>> und <<src-recipe-form,`RecipeForm`>> bekommen
  ihre Daten als Props. <<src-recipe-detail,`RecipeDetail`>> fällt aus dem Muster – es lädt sein Rezept selbst und wird von
  `RecipeDetailPage` nur mit der `id` versorgt.

| <<src-api-recipes,`src/api/recipes.ts`>>
| Der einzige Ort, an dem `fetch` aufgerufen wird. Wirft bei Nicht-2xx einen `ApiError`,
  der das Problem Detail des Backends trägt – `fieldError(name)` liefert damit die
  Validierungsmeldung an das verursachende Feld.

| `src/api/schema.d.ts`
| Aus dem OpenAPI-Contract *generiert* und eingecheckt. Die TS-Typen der API sind damit
  nicht von Hand gepflegt – und deshalb nicht im Anhang, siehe <<quelldateien>>.
|===

Die Fehlerbehandlung des Frontends hängt so direkt am Contract: Ändert das Backend ein
Feld, fällt es nach dem Neugenerieren der Typen beim `tsc`-Lauf des Builds auf.

<<src-gruppe-frontend>> enthält zusätzlich den Einstiegspunkt `src/main.tsx`, die
`index.html` und das Stylesheet – Dateien, die keine Aussage über die Struktur treffen und
deshalb oben nicht aufgeführt sind.
