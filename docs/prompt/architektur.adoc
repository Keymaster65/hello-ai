= Skill: Java-Architektur

== Zweck

Aktiviere diesen Skill bei Design-Entscheidungen, neuen Modulen, Refactorings oder
Struktur-Fragen.

== Prinzipien

* *Layered / Clean Architecture*
* *SOLID-Prinzipien*
* *Dependency Injection* (Konstruktor-Injektion)
* *Separation of Concerns*

== Package-Struktur

----
io.github.keymaster65.helloai
├── adapter.in.rest            → REST-Endpoints (Controller)
├── adapter.out.persistenz     → Datenzugriff (Infrastructure)
├── application.port.in        → Business-Logik eingehende ports
├── application.port.out       → Business-Logik ausgehende ports
├── application.service        → Business-Logik (Application)
├── domain.model               → Entities, Domain-Modelle, Value Objects
├── domain.services            → Domänenlogik ohne eigenen Modelltyp (ADR 0020)
├── bootstrap                  → Spring Anwendung (main)
----

== Schichten & Abhängigkeitsregel

----
bootstrap → adapter  →  application  →  domain
----

Abhängigkeiten zeigen nach innen. Controller kennt keine Entities direkt.

Diese Regel ist *doppelt abgesichert*:

. *Vom Build erzwungen* – jede Schicht ist ein eigenes Gradle-Modul unter `:modules:backend`
  (`:modules:backend:bootstrap` → `:modules:backend:adapter` → `:modules:backend:application` →
  `:modules:backend:domain`). Ein Import aus einer äußeren Schicht *compiliert nicht*; siehe
  link:{adr}/0013-ein-gradle-modul-je-schicht{adrext}[ADR 0013] und
  link:{adr}/0014-schichtmodule-unter-backend{adrext}[ADR 0014] sowie
  link:{adr}/0015-alle-bausteine-unter-modules{adrext}[ADR 0015].
. *Von ArchUnit geprüft* – `LayeredArchitectureTest` sichert zusätzlich ab, was Modulgrenzen
  nicht sehen: Framework-Freiheit von Domäne *und* Anwendungsschicht und „Ports sind
  Interfaces"; siehe link:{adr}/0012-archunit-fuer-die-schichtenregel{adrext}[ADR 0012] und
  link:{adr}/0045-anwendungsschicht-frei-von-frameworks{adrext}[ADR 0045].
  `OnionArchitectureTest` beschreibt dieselbe Struktur als Zwiebelschalen und schließt die
  Lücke der Schichtensicht: *Adapter kennen einander nicht* – der REST-Adapter greift nicht
  am Port vorbei auf die Persistenz zu. Siehe
  link:{adr}/0019-onion-architecture-regel-in-archunit{adrext}[ADR 0019].

Fehlt einer Klasse eine Abhängigkeit, ist das ein Hinweis auf einen Schichtverstoß – nicht
die Aufforderung, sie im Buildskript zu ergänzen.

== Die inneren Schichten sind framework-frei

`domain` und `application` enthalten *keinen* Framework-Typ – kein Spring, kein jOOQ, kein
Jakarta, kein Jackson, kein Liquibase
(link:{adr}/0045-anwendungsschicht-frei-von-frameworks{adrext}[ADR 0045]). Das ist keine
Stilfrage: Geschäftsregeln, die an einer Laufzeit hängen, sind nur mit dieser Laufzeit prüfbar.

Das gilt *auch für Annotationen*. `+@Service+` und `+@Transactional+` sind Abhängigkeiten wie
jeder Import; `+@Transactional+` obendrein eine, deren Wirkung außerhalb eines Spring-Kontexts
schlicht ausbleibt – die Zusicherung stünde in der Schicht, einlösbar wäre sie nur außerhalb.

Beides ist doppelt abgesichert, und die stärkere Sicherung ist die *strukturelle*:

* *Der Build.* `+:modules:backend:application+` deklariert außer `+:domain+` keine
  Produktionsabhängigkeit. Eine Framework-Annotation dort *compiliert nicht*.
* *ArchUnit.* `application_is_free_of_frameworks` in `LayeredArchitectureTest` – die
  Schwesterregel zu `domain_is_free_of_frameworks`. Sie greift, sobald jemand die Abhängigkeit
  wieder ins Buildskript einträgt.

IMPORTANT: Eine fehlende Abhängigkeit in `+:application+` ist deshalb *nie* der Anlass, sie zu
ergänzen – sondern die Aufforderung, den Framework-Bedarf nach außen zu verlegen.

=== Was stattdessen wohin gehört

[cols="1,2", options="header"]
|===
| Bedarf | Ort

| Bean-Erzeugung („wer instanziiert den Dienst?")
| `+@Bean+`-Methode im Composition Root `+:bootstrap+` (`ApplicationServicesConfig`) – nicht
  `+@Service+` an der Klasse. Der Anwendungsdienst ist mit `+new+` instanziierbar.

| Transaktionsgrenze
| Ein Dekorator im Composition Root, der den *eingehenden Port* implementiert und mit
  `TransactionTemplate` umschließt (`TransactionalRecipeService`). Die Grenze bleibt der Use
  Case; nur ihre Formulierung steht außerhalb.

| Web, Serialisierung, SQL
| Adapter. Sie *sind* die Schicht, die das Rahmenwerk kennt – dort bleiben
  `+@RestController+`, `+@Repository+` und `+@RestControllerAdvice+`.
|===

WARNING: Wächst ein eingehender Port um einen Use Case, wächst der Dekorator mit. Wird er
vergessen, läuft der neue Use Case *ohne Transaktion* – still, denn ArchUnit sieht im Bytecode
nicht, ob eine Delegation in einem `TransactionTemplate` steckt (ADR 0045, „Nachteile").

== Records: Currying ab drei Komponenten

Jeder `record` mit *mehr als zwei* Komponenten bietet eine curried Factory `curried()` – eine
Kette einstelliger Schritte, je einer pro Komponente, benannt wie die Komponente. Damit
erzwingt der Compiler Reihenfolge und Vollständigkeit, und die Namen stehen an der
Aufrufstelle statt nur in der Deklaration.

[source,java]
----
public record Ingredient(String name, BigDecimal quantity, String unit) {

    public static NameStep curried() {
        return name -> quantity -> unit -> new Ingredient(name, quantity, unit);
    }

    @FunctionalInterface
    public interface NameStep {
        QuantityStep name(String name);
    }
    // QuantityStep → UnitStep → Ingredient
}

Ingredient ingredient = Ingredient.curried()
        .name("Spaghetti")
        .quantity(BigDecimal.valueOf(500))
        .unit("g");
----

Der kanonische Konstruktor bleibt der einzige Ort der Validierung; die Kette ruft ihn im
letzten Schritt auf. `RecordCurryingTest` prüft die Form der Kette – nicht nur, dass es eine
Methode `curried()` gibt. Begründung und Grenzen:
link:{adr}/0021-currying-fuer-records-mit-mehr-als-zwei-komponenten{adrext}[ADR 0021].

== Checkliste vor Implementierung

. Welche Schicht ist betroffen?
. Trifft es `domain` oder `application`: Kommt der Entwurf *ohne* Framework-Typ aus? Wenn
  nicht – welcher Teil davon gehört in den Composition Root oder in einen Adapter?
. Gibt es ein Interface für den Service/Repository?
. Ist die Komponente per Mock testbar – *ohne* Spring-Kontext?
. Werden Entities über DTOs von der API entkoppelt?
. Ist Exception-Handling zentral (`@ControllerAdvice`)?

== Beispiel: sauberer Anwendungsdienst

Gewöhnliches Java: keine Annotation, kein Lombok
(link:{adr}/0003-kein-lombok-records-und-konstruktor-injektion{adrext}[ADR 0003]),
Konstruktor-Injektion von Hand.

[source,java]
----
public class UserService implements UserUseCases {   // der eingehende Port

    private final UserRepository userRepository;     // der ausgehende Port
    private final UserMapper userMapper;

    public UserService(UserRepository userRepository, UserMapper userMapper) {
        this.userRepository = userRepository;
        this.userMapper = userMapper;
    }

    @Override
    public UserDto findById(Long id) {
        return userRepository.findById(id)
                .map(userMapper::toDto)
                .orElseThrow(() -> new UserNotFoundException(id));
    }
}
----

== Beispiel: Verdrahtung im Composition Root

Hier – und nur hier – wird das Rahmenwerk sichtbar: Bean-Erzeugung und Transaktionsgrenze
(link:{adr}/0045-anwendungsschicht-frei-von-frameworks{adrext}[ADR 0045]).

[source,java]
----
@Configuration
class ApplicationServicesConfig {

    /** Die einzige Bean des Ports: die Use Cases, umschlossen von der Transaktionsgrenze. */
    @Bean
    UserUseCases userUseCases(
            UserRepository repository,
            UserMapper mapper,
            PlatformTransactionManager transactionManager) {
        return new TransactionalUserUseCases(
                new UserService(repository, mapper), transactionManager);
    }
}
----

== Beispiel: Controller (dünn, ohne Business-Logik)

[source,java]
----
@RestController
@RequestMapping("/api/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @GetMapping("/{id}")
    public ResponseEntity<UserDto> getUser(@PathVariable Long id) {
        return ResponseEntity.ok(userService.findById(id));
    }

    @PostMapping
    public ResponseEntity<UserDto> createUser(
            @Valid @RequestBody CreateUserRequest request) {
        UserDto created = userService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(created);
    }
}
----

== Beispiel: zentrales Exception-Handling

[source,java]
----
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(
            UserNotFoundException ex) {
        var error = new ErrorResponse(HttpStatus.NOT_FOUND.value(),
                                      ex.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }
}
----

== Anti-Patterns vermeiden

* Business-Logik im Controller
* Framework-Annotation in `domain` oder `application` – auch `@Service` und `@Transactional`
  sind Abhängigkeiten (ADR 0045)
* Eine fehlende Abhängigkeit in einer inneren Schicht im Buildskript nachtragen
* `@Autowired` auf Feldern (nutze Konstruktor-Injektion)
* Entities direkt als API-Response zurückgeben
* Fat Services / God-Classes
* Zirkuläre Abhängigkeiten zwischen Komponenten
* Feld-Injektion erschwert Testbarkeit
